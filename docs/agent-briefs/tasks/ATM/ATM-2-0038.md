# [ATM-2-0038] Unified Atom Generator — Provisioning Facade & ID Allocator

> **ATM 原子產生器開卡** — 建立 `AtomGenerator` 作為新原子誕生的唯一正式入口（Provisioning Facade），收編 ID 配發、spec 初始化、scaffold、registry 登錄、catalog 同步等共用流程，終結「每次建原子都要手動串 5 個 primitive」的現狀。
> **定位**：ATM-2（provisioning architecture / single entrypoint / facade）
> **前置依賴**：ATM-2-0002（Scaffold Builder）/ ATM-2-0004（Registry & HashLock）/ ATM-2-0013（Atom Space Layout）/ ATM-2-0037（Alias Drift Guard）

---

## 1. 問題診斷

### 1.1 架構缺口

Roadmap §4.5 定義 **Atomic Manager** 應同時扮演 13 個角色（spec parser、scaffolder、registry updater…），但實際實作中這 13 個能力被拆成獨立 primitive，且沒有任何一層把它們串在一起：

| 已存在的 primitive | 位置 | 做什麼 | 不做什麼 |
|---|---|---|---|
| `parseAtomicSpecFile()` | `core/src/spec/parse-spec.mjs` | 讀 + 驗 spec JSON | 不產生 spec、不配 ID |
| `scaffoldAtomWorkbench()` | `core/src/manager/scaffold.mjs` | 從 normalizedModel 產出 workbench 檔案 | 假設 caller 已帶入 atomId |
| `createAtomicRegistryEntry()` | `core/src/registry/registry.mjs` | 產生 registry entry | 不觸發 scaffold |
| `createAtomSpaceLayout()` | `core/src/manager/atom-space.mjs` | 解析 canonical 路徑 | 不配 ID、不寫檔 |
| `createSourceHashSnapshot()` | `core/src/hash-lock/hash-lock.mjs` | 計算 spec/code/test hash | 被 registry 呼叫，不獨立觸發 |

**問題**：這些 primitive 之間沒有一個 orchestrator。每次「建立一個新原子」需要手動依序呼叫 5+ 個函式，且 ID 配發由 caller 自行硬編。

### 1.2 具體散亂證據

- CLI（`atm.mjs`）目前 8 個 command：`bootstrap / init / self-host-alpha / spec / status / test / validate / verify`——**沒有 `create` 或 `generate`**
- `atomic-registry.json` 現有 entry 的 atomId（`ATM-CORE-0001`、`ATM-CORE-0003`、`ATM-FIXTURE-0004`）由手動/各腳本各自編號，無集中 allocator
- Roadmap §7 Genesis Map 畫出 000001→000008 的 DAG，但沒有一個 named function 封裝這個 DAG 的「建立」子集

### 1.3 此卡要解的核心問題

> **把「建立新原子」從一組散落的 primitive 呼叫，收斂成一個有名字、有契約、有測試的 Facade。**

### 1.4 硬性約束：原子產生器自己也必須是原子

> **⛔ 這不是建議，是不可妥協的硬性約束。**

原子產生器不得以「裸 helper function」或「host 端工具腳本」的身分存在。它**自己就是一顆原子**（或由多顆原子組成的 Atom Map），受到框架治理體系的完整管轄：

| 治理項目 | 要求 |
|---|---|
| **Atomic Spec** | 必須有自己的 `atom.spec.json`，定義 input/output schema、sideEffects、dependencyPolicy |
| **Atomic ID** | 必須配發正式 atomId（預計 `ATM-CORE-0005` 或由 allocator 實際配發） |
| **Registry Entry** | 必須登錄進 `atomic-registry.json`，被 drift checker / hash-lock 管理 |
| **Canonical Workbench** | 必須住在 `atomic_workbench/atoms/<atomId>/`，遵守 ATM-2-0013 layout |
| **Atomic Test** | 必須有 `atom.test.ts`，通過 `atm test` 驗證 |
| **Hash Lock** | spec/code/test 三重 hash 必須被 lock，registry 可偵測 drift |
| **Evidence** | 必須產出 `atom.test.report.json`，被 evidence 管線收錄 |

**為什麼這麼堅持？**

這是 Roadmap §6 自舉原則的直接體現：「用原子方法建立原子框架本身」。如果框架最核心的「建立原子」能力本身不是原子，等於第一天就破壞自己的哲學。後果是：

1. Generator 的代碼不受 Police 管轄（瘦身警察、關係警察、規格漂移警察都抓不到它）
2. Generator 的品質無法被 `atm test` / `atm validate` 驗證
3. Generator 變成框架裡唯一的「特權公民」，所有治理規則對它無效
4. 其他 Agent 無法用 registry 查詢 generator 的能力、版本、hash

**自舉悖論的解法**：

Generator 自己還不存在時，無法用 `atm create` 建自己。採用 Roadmap §7 Genesis Bootstrap 模式：

```
Phase 1 — 手動 bootstrap：
  人工或 AI 寫出 generator 的 atom.spec.json
  → 手動放入 atomic_workbench/atoms/ATM-CORE-XXXX/
  → 手動寫 atom-generator.mjs 作為 atomic code
  → 手動跑 atm test + atm validate 確認通過

Phase 2 — 登錄：
  用 registry primitive 手動建立 registry entry
  → hash-lock 鎖定 spec/code/test hash
  → 寫入 atomic-registry.json

Phase 3 — Dogfood 驗證：
  用剛落地的 generator（atm create）建一顆 FIXTURE atom
  → 證明 generator 能產生合規原子
  → 這顆 FIXTURE atom 的存在本身就是 generator 的 evidence
```

完成 Phase 3 後，generator 同時滿足兩個身分：
- **作為原子**：被 registry / police / hash-lock / test runner 管理
- **作為工具**：被 CLI `atm create` 和其他 Agent 呼叫

## 2. 設計規格

### 2.1 AtomGenerator — 核心 Facade（同時是一顆受治理的原子）

**物理位置**（雙重身分）：

```
packages/core/src/manager/atom-generator.mjs   ← runtime code（被 CLI 引用）
atomic_workbench/atoms/ATM-CORE-XXXX/          ← canonical atom home
  atom.spec.json                                ← 自己的 Atomic Spec
  atom.test.ts                                  ← 自己的 Atomic Test
  atom.test.report.json                         ← 自己的 test evidence
```

> `packages/core/…` 是 runtime 引用路徑；`atomic_workbench/…` 是治理住址。
> registry entry 的 `location.codePaths` 指向前者，`location.workbenchPath` 指向後者。
> 這與現有 ATM-CORE-0001（seed）的模式一致：spec 在 `specs/`，code 在 `packages/core/`，workbench 在 `atomic_workbench/atoms/ATM-CORE-0001/`。

**Generator 的 Atomic Spec 骨架**（`atom.spec.json` 關鍵欄位）：


### 2.2 內部執行管線

`generateAtom()` 內部嚴格按以下順序委派已有 primitive：

```
Step 1 ─ allocateAtomId(bucket, registryPath)     → atomId
         ↓
Step 2 ─ initMinimalSpec(atomId, request)          → normalizedModel
         ↓
Step 3 ─ scaffoldAtomWorkbench(normalizedModel)    → scaffold result
         ↓
Step 4 ─ createAtomicRegistryEntry(normalizedModel) → registry entry
         ↓
Step 5 ─ appendRegistryAndWriteArtifacts()         → updated registry + catalog
```

**設計約束**：
- 每個 step 若失敗，整個管線中止並返回 `{ ok: false, failedPhase, error }`
- Step 1–3 為冪等（相同 request 重跑不重複領號、不覆蓋已存在的 workbench）
- Step 4–5 受 `dryRun: true` 控制，dry-run 時只產出 preview 不寫 registry
- **不新增邏輯**——每個 step 都委派已存在的 primitive，generator 只負責串接與錯誤處理

### 2.3 ID Allocator

新增 `packages/core/src/manager/id-allocator.mjs`：

```js
/**
 * 從現有 registry 掃描已使用的 sequence number，配發下一個可用 ID。
 * @param {string} bucket - e.g. "CORE", "FIXTURE", "PLUGIN"
 * @param {object} [options]
 * @param {string} [options.registryPath] - 預設 atomic-registry.json
 * @param {string} [options.repositoryRoot]
 * @returns {{ atomId: string, bucket: string, sequence: number }}
 */
export function allocateAtomId(bucket, options = {})
```

**配發規則**：
- 格式固定為 `ATM-{BUCKET}-{NNNN}`（4 位零填充）
- 掃描 `atomic-registry.json` entries 中同 bucket 的最大 sequence，+1
- 若 registry 不存在或為空，從 `0001` 開始
- 不做 reservation file（alpha0 簡化），但 API 預留 `reservation` 欄位供 alpha1 擴充
- 不跳號填補（max+1 政策，不回填中間缺號）

**已知 bucket 清單**（可擴充，不硬鎖）：

| bucket | 用途 |
|---|---|
| `CORE` | 框架自身核心原子 |
| `FIXTURE` | 測試用 fixture 原子 |
| `PLUGIN` | plugin 附帶原子 |
| `HOST` | host project 專屬原子 |

### 2.4 CLI `create` 命令

新增 `packages/cli/src/commands/create.mjs`，註冊到 `atm.mjs` 的 `cliCommandRunners`：

```bash
atm create --bucket CORE --title "ParseHtmlToDom" \
           --description "Parse HTML string into normalized DOM tree." \
           --logical-name "atom.core-parse-html"
```

**行為**：
- 呼叫 `generateAtom()` 並以標準 CLI JSON 格式輸出結果（走 `makeResult` + `writeResult`）
- 支援 `--dry-run`：只回傳 preview，不寫任何檔案
- exit code：0 = ok, 1 = generation failed, 2 = invalid args
- CLI 僅作 facade——核心邏輯全在 `atom-generator.mjs`

## 9. 設計決策記錄

| # | 決策 | 理由 |
|---|---|---|
| D-1 | Generator 作為 Facade 而非 Factory/Builder | 不是動態建立多態物件，是固定管線的統一入口；Facade 語意最精確 |
| D-2 | ID Allocator 讀 registry 而非獨立 sequence file | alpha0 原子數量 < 100，不需額外 state file；registry 就是 single source of truth |
| D-3 | 不跳號填補（不回填中間缺號） | 簡化邏輯、避免 ID 被回收後又被引用的混亂；max+1 政策 |
| D-4 | CLI 預設 JSON 輸出 | 與現有 CLI pattern 一致（所有命令都走 `makeResult` + JSON stdout） |
| D-5 | 不處理演化管線 | 本卡定義為 `lifecycleMode = birth`；evolution 屬 alpha1（見 ATM框架演進執行規劃書 §2.1） |
| D-6 | forbidden_files 包含所有既有 primitive | 強制 generator 走委派、禁止直接修改已穩定的底層模組 |
| D-7 | Generator 本身必須是原子（硬性約束） | 框架哲學要求自舉（Roadmap §6）。Generator 若不是原子，就是框架裡唯一的特權公民——Police 抓不到它、hash-lock 管不了它、atm test 驗不了它。這不可接受。Phase E 自舉登錄是本卡的驗收門檻，不是 nice-to-have |

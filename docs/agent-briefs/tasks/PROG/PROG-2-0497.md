## 完整描述
DS-02 驗收條件：GeneralUnit 型別與 generals.json 涵蓋規格範例全部欄位並通過 schema 驗證。
本卡交付可獨立驗證的部分：把規格 §二.1 的 22 個欄位與其列舉、形狀規則寫成純 TS 契約，並提供覆蓋率計數。
不在本卡：替 generals.json 補資料（見阻塞）。

## 設計選擇（我的判斷）
- 契約只驗「欄位存在時」的形狀，缺欄位不報錯，避免現有 235 筆因尚未補資料而全部失敗。
- 列舉照規格 §2-2 #28、#30、#31、#31a、#2 逐條實作（Revelation_Level、故事條六槽、Default_Tab、StoryDock、Female_Role_Type）。
- Prowess_Stats.Source_Session_ID 允許 null，依 #29 表示尚無畢業快照，不回填戰力值。
- 新檔放在 core/models，與 GeneralSchema.ts（MVP-01 舊欄位）並存；舊欄位不改，避免動到存檔格式。

## 覆蓋現況（generals.json，235 筆）
- 已有：Template_ID→templateId、Bloodline_ID→bloodlineId、Status、Role、Stats、Vitality、Vitality_Max→maxVitality、Core_Tags→coreTags（皆為舊 camelCase 欄位名，235/235）。
- 缺：Phase、Has_Retired_Before、Female_Role_Type、Talent_Stats、Prowess_Stats、Personality、Loyalty、Recent_Log、Current_Suitability、Father_ID、Mother_ID（0/235）。
- 形狀不同：Genes（規格 Type/ID/Level/Is_Locked/Discovery_Level；資料為 id/displayName/type 中文/level）、Ancestors_JSON（規格為三代樹；資料為摘要字串 ancestorsSummary）、Profile_Presentation（規格為物件；資料為扁平 storyStripCells）。

## 需 PM 裁定（阻塞）
1. Talent_Stats 的 Base / Current / Max_Potential 數值來源（設計表或暫定公式）。
2. Prowess_Stats 是否只在畢業快照後才寫入（目前規格允許 Source_Session_ID 為 null）。
3. Father_ID / Mother_ID 來源（家族關係系統或本卡之外）。
4. Genes、Ancestors_JSON、Profile_Presentation 以規格形狀為準改寫資料，或保留舊形狀並在契約加映射。

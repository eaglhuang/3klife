## 完整描述
FUL-06 要求 Server 有 `Player_Level`、`Unlock_Phase` 欄位，玩家升級跨過階段時能持久化，並觸發 Phase 2／3 的通知。
本卡交付 schema 與純 TS 邏輯，通知文案不在範圍內。

- `server/schema/003_player_unlock_state.sql`：`player_unlock_state` 表，主鍵 `player_id VARCHAR(32)`，`player_level ≥ 1`，`unlock_phase` 限 1~3。未執行。
- `server/schema/ful06-unlock-phase.ts`：
  - `phaseForLevel`：Lv1~20 → 1、Lv21~45 → 2、Lv46+ → 3。
  - `detectPhaseCrossing`：升級時回報新跨過的階段（一次跨兩階段會列出兩個）。
  - `advancePlayerUnlockState`：升級並寫回階段，非正整數等級直接丟錯。
  - `validatePlayerUnlockStateRow`：擋下階段與等級不符、階段超界、player_id 過長。

## 設計選擇（我的判斷）
- 門檻取規格 §I 的 DiscoveryThresholds（Phase1: 20、Phase2: 45），由函式參數覆寫，不寫死在 SQL。理由：規格明說門檻由 config 管理，DDL 的 CHECK 若寫死就得每次改門檻都要遷移。因此 SQL 只限範圍，階段一致性由 TS 驗證負責。
- 規格表的 Discovery_Level 與 config 的 Phase1／Phase2 數值一致地解讀為「該階段最高等級（含）」，即 Lv20 仍是 Phase 1。
- 跨階段只回傳跨越資訊，不發通知，留給日後接線。

# TASK-MEM-0009 Evidence preservation across close windows

Fix BUG-ATM-0074's data-loss chain observed live under two-captain
parallelism (TASK-MEM-0003/0004/0007 close storm, 2026-07-14/15):

1. Captain A's close window defers Captain B's governance-dirty evidence file
   into `.atm/runtime/snapshots/close-window-governance-dirty-...` and clears
   the worktree copy.
2. `classifyAutoGeneratedResidue` marks a FOREIGN close-window snapshot
   `auto-clean-safe`/`remove`, so any other pre-commit hook run deletes A's
   snapshot before A restores it.
3. `restoreDeferredGovernanceDirtyFiles` then reports `snapshot-missing` and
   the evidence is permanently gone. Separately, a close failure thrown
   between defer and the restore call sites can skip restore entirely.

## Acceptance

- `cleanupAutoGeneratedResidue` (hook) refuses to remove a
  close-window-governance-dirty snapshot whose recorded `restoredAt` is null
  (unconsumed deferral) — regardless of owner; consumed snapshots
  (`restoredAt` set) stay auto-cleanable.
- The taskflow close write path guarantees
  `restoreDeferredGovernanceDirtyFiles` runs on every exit (try/finally),
  including thrown CliErrors between defer and commit.
- Regression: an unconsumed foreign snapshot survives a hook cleanup pass; a
  consumed one is removed.

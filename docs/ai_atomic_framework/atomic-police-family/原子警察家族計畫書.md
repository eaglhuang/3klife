# 原子警察家族計畫書

## 0. 核心結論

原子警察不是沒有落地，而是「部分落地、概念分散、尚未產品化成完整警察家族」。

目前 AI-Atomic-Framework 已經具備 police runtime、validator、schema、fixture、status machine、map-curator、guidance、neutrality scanner 與 lifecycle-police 等能力；但 Dedup Police、Demand Police、Atomization Police、Quality Police、Map Integration Police 等名稱，尚未全部以獨立 police plugin / scanner / report producer 的方式交付。

本文件區是 3KLife 內部的 upstream roadmap / control plane，用來把散落的實作盤點成可執行的產品化路線。真正 runtime 實作仍以 `C:/Users/User/AI-Atomic-Framework` 為 upstream truth；本目錄只負責規劃、任務拆分、狀態追蹤與後續 promotion gate 定義。

## 0.1 2026-05-18 修訂結論

本輪修訂是 contract wording / roadmap 精修，不代表 named police scanners 已全部 runtime 落地。`TASK-APF-*` 的 `done` 在本文件區只表示「文件 / spec artifact 已完成」，不得解讀為 AI-Atomic-Framework upstream runtime 已完成產品化。

本輪修補鎖定 6 個判讀風險：補列 upstream 第 7 種 `PoliceCheckKind = dependency-graph`、避免 `PoliceFinding` 與既有 `LifecyclePoliceFinding` / `ReviewAdvisoryFinding` 衝突、拆清 upstream official evidence type 與 police-local artifact/readModel ref、逐 police 標出 advisory / blocker 進場門檻、把 alpha 排程與 shadow adapter pathway 寫回主文件、精準引用 `dedup-merge.ts`、`neutrality-scanner.ts` 與 `map-curator` 4 signal。

2026-05-18 M7 追加結論：警察家族不能只停在 roadmap。最低守關定義改為「必須能被 validator profile 啟動，且每次 gate 執行時會產生 machine-readable report / finding」。尚未 named scanner 產品化的 Dedup / Demand / Map Integration / Atomization，也必須先以 advisory adapter 進 `validate:standard` 或 `validate:full`，否則只能標 embedded / planned，不得標為 `gate-active`。

## 1. 狀態標記

| 狀態 | 定義 | 產品化含義 |
|---|---|---|
| `implemented` | 已有獨立 runtime/plugin/scanner 或 validator 可直接執行 | 可先納入 police family contract，只需補統一 report facade |
| `embedded` | 功能已存在，但散在 validator、map-curator、guidance、status-machine、lifecycle-police 等模組 | 需要命名、抽 facade、補 finding contract |
| `fixture-only` | schema / fixture / 測試語意存在，但尚未有正式 runtime scanner | 先補 scanner 或 report producer，再接 orchestrator |
| `missing runtime scanner` | 文件或 route 已提到，但缺少可重跑 scanner / report producer | 必須開卡補 deterministic runtime，不可宣稱完成 |
| `gate-active` | 已接入 validator profile，會被 `validate:standard` 或 `validate:full` 呼叫並產生 machine-readable report / finding | 進入守關狀態；blocker family 可 fail gate，advisory family 至少必須出 report |

## 4. 產品化原則

1. 不建立第二套 approval workflow。所有 police finding 都必須回到既有 UpgradeProposal、ReviewAdvisory、HumanReviewDecision、registry transitions 或 follow-up-task route。
2. **不新增獨立任務路由器**：route 透過「`ReviewAdvisory.machine-finding` + `HumanReviewQueue` + 既有 follow-up-task」三個既有接點完成。
3. 不直接 mutate registry。除了已定義的 lifecycle quarantine writer 權限外，其他 police family 預設只能輸出 report、finding、proposal draft 或 follow-up route。
4. 不把 embedded implementation 直接改名成獨立 plugin。先保留 `map-curator`、`regression-compare`、`guidance`、`neutrality-scanner` 的既有邊界，再在外層加 family facade。
5. 不硬寫 3KLife / Cocos / 私有 repo 語意到 AI-Atomic-Framework protected public surface。
6. 所有 police surface 必須輸出 machine-readable finding，至少包含 `trigger / scope / severity / action / routeHint / readModel / mode`。
7. fast police 走 deterministic validator / CI；slow police 走 scheduled scan / advisory report / review queue。逐 police 的 advisory / blocker 標記見 §7 里程碑表與 APF-0010 backwrite。
8. M7 之後，可稱為「警察守關」的最低門檻是 `gate-active`：至少要在 validator profile 被啟動並輸出 report / finding；只存在文件、fixture 或 embedded module 不足以宣稱守關。

## 5. 共用 PoliceFinding contract 方向

未來 upstream 可新增共用 finding 型別，但本文件落地階段不直接修改 API。建議 contract 欄位如下：

| 欄位 | 說明 |
|---|---|
| `findingId` | 穩定 finding id，可重跑比對 |
| `policeFamily` | `dedup`、`demand`、`quality`、`map-integration`、`atomization`、`lifecycle`、`boundary`、`dependency-graph`、`registry-consistency`、`schema`、`orchestrator` |
| `behaviorId` | 可選；finding 建議路由到的 `behavior.*` |
| `trigger` | 觸發事件，例如 `semantic-fingerprint-overlap`、`caller-demand-threshold`、`map-propagation-failed` |
| `scope` | 掃描範圍，例如 registry、map、evidence、legacy route plan、quality report |
| `severity` | `info / advisory / warning / block / error` |
| `action` | `report-only`、`propose`、`follow-up-task`、`needs-review`、`quarantine`、`hard-fail` |
| `routeHint` | 給 ReviewAdvisory.machine-finding / HumanReviewQueue / follow-up-task 的路由提示（不新增獨立任務路由器） |
| `readModel` | 對應 index / snapshot / metrics / report path |
| `mode` | `fast` 或 `slow` |
| `evidenceRefs` | 可重跑證據引用 |

### 5.1 與既有 finding type 的相容性

- **lifecycle-police 沿用既有 `LifecyclePoliceFinding`**（含 `trigger / scope / severity / action / route / message`），不另立第三套。
- **其他 10 個 police family** 統一以 `ReviewAdvisoryFinding.trigger = machine-finding` 入 advisory queue；PoliceFinding 預設放在既有 `ReviewAdvisoryFinding.metadata.policeFinding`，不得宣稱 upstream 已有 `payload` 欄位。
- `payload` 只能作為未來 additive API proposal 討論；在 upstream API 未變更前，文件與任務卡一律以 `metadata.policeFinding` 為預設實作路徑。
- **upstream 獨立任務路由器不存在**：實作上等同於 `ReviewAdvisoryFinding.routeHint` + `HumanReviewQueue` + 既有 `follow-up-task` 任務卡產生流程。
- **APF-0012 負責把 PoliceFinding 與 ReviewAdvisory.machine-finding 串接**，含 evidence schema bridge 與 routing rule。

### 5.2 severity / action 映射

| PoliceFinding severity | ReviewAdvisory severity / action | blocking 語意 |
|---|---|---|
| `info` | `info` + `monitor` | report-only，不阻塞 |
| `advisory` | `low` + `needs-review` 或 `monitor` | 進 advisory queue，不直接 fail CI |
| `warning` | `medium` + `needs-review` | 需要 reviewer 看，但不等同 hard fail |
| `block` | `high` + `request-human-review` | 只有該 family 已在 profile 中標為 blocker 時，才造成 deterministic fail |
| `error` | lifecycle / boundary / dependency-graph / schema 等既有 hard fail；其他 family 先進 ReviewAdvisory | 不得由新 scanner 自行繞過既有 gates |

Lifecycle Police 自身仍使用 `LifecyclePoliceSeverity = info / warning / error`；wrapper 若要輸出 PoliceFinding view，需依上表映射，不改動既有 lifecycle report schema。

### 5.3 evidenceRefs / readModel 分層

`evidenceRefs` 不得把所有 artifact ref 都宣稱成 upstream `EvidenceRecord.evidenceType`。本計畫採兩層命名：official evidence type 使用 upstream 既有 `EvidenceRecord.evidenceType`；其他 scanner output 先作為 police-local artifact/readModel ref，直到 upstream schema 另行 additive 擴充。

| 類型 | 可用值 | 用途 |
|---|---|---|
| upstream official `EvidenceRecord.evidenceType` | `usage-feedback`、`quality-baseline`、`quality-comparison`、`rollback-proof`、`human-review-decision` | 可直接對應 upstream `EvidenceRecord.evidenceType` |
| police-local artifact/readModel ref | `fingerprint-snapshot`、`map-propagation-log`、`neutrality-scan`、`dep-graph-snapshot`、`caller-graph-snapshot`、`dry-run-patch` | 可重跑 scanner / report 的 artifact path 或 URI，不宣稱為 official evidence type |

| PoliceFinding ref | 分層 | 來源 |
|---|---|---|
| `usage-feedback` | official evidence type | `ATOM_EVOLUTION_PLAN.md` evidence model |
| `quality-baseline` | official evidence type | quality baseline evidence |
| `quality-comparison` | official evidence type | `regression-compare` output |
| `rollback-proof` | official evidence type | rollback proof evidence |
| `human-review-decision` | official evidence type | HumanReviewDecision evidence |
| `fingerprint-snapshot` | police-local artifact/readModel ref | `RegistryIndex` semantic fingerprint snapshot |
| `map-propagation-log` | police-local artifact/readModel ref | `map-curator` propagation report |
| `neutrality-scan` | police-local artifact/readModel ref | `neutrality-scanner` report |
| `dep-graph-snapshot` | police-local artifact/readModel ref | `dependency-graph.ts` output |
| `caller-graph-snapshot` | police-local artifact/readModel ref | caller distribution / graph snapshot |
| `dry-run-patch` | police-local artifact/readModel ref | dry-run proposal envelope |

`readModel` 一律指向 artifact path / URI / snapshot id；它是重跑與比對入口，不是新的 storage authority。

### 7.1 目前 upstream profile 與 APF 目標 profile

目前 AI-Atomic-Framework 的 `validators.config.json` 中，`validate:police` 屬於 `full` profile；`validate:map-curator` 與 `validate:regression-compare` 已在 `standard` profile。APF 計畫中的 quick / standard / full family registry 是未來 orchestrator 目標，不是現況宣告。

APF 目標政策：

- `validate:quick` → 僅含 Schema / Boundary / Dependency Graph / Lifecycle 等 fast blocker check。
- `validate:standard` → 加上 Map / Quality / Registry Consistency；新 named police 初期以 advisory 進場。
- `validate:full` → 全部 police family 啟動；advisory 升 blocker 需滿足「兩階段 fixture pass + 連續兩個 release advisory pass + ReviewAdvisory false-positive < 5%」。

### 7.2 Alpha 排程與 shadow adapter pathway

| 階段 | APF 目標 | 說明 |
|---|---|---|
| alpha0 | contract surface 凍結 | APF-0001 / 0002 / 0011 / 0012 只定義 public-neutral contract 與 bridge，不宣稱 scanner 已落地 |
| alpha1 | Default Governance Bundle / named scanner 試跑 | APF-0003 ~ 0008 以 advisory report / wrapper 方式進場 |
| alpha1+ | orchestrator 與 advisory→blocker promotion | APF-0009 / 0010 定義 profile 與升級條件 |

3KLife 的私有 routing 只能存在 shadow adapter / adopter governance bundle 層：

```text
3KLife adopter docs
  -> shadow adapter / adopter governance bundle
  -> AI-Atomic-Framework upstream police runtime
  -> ReviewAdvisory.machine-finding
  -> HumanReviewQueue / follow-up-task route
```

upstream police runtime 必須保持 adopter-neutral；不得把 3KLife / Cocos / private path 寫入 public protected surface。

## 8. 驗證策略

文件落地驗收：

- 本目錄與所有 task cards 皆有 `doc_id`。
- Markdown 是 UTF-8 without BOM，且無 U+FFFD / mojibake。
- `tasks/README.md` 索引連到所有 `TASK-APF-*`。
- 主計畫書明確標示 `implemented / embedded / fixture-only / missing runtime scanner / gate-active`。
- 不把 3KLife-specific 規則寫成 AI-Atomic-Framework protected public contract。

後續 upstream 實作驗收：

- `validate:police` 維持通過。
- `validate:standard` 會執行 `validate-police-family`；core blocker family 可造成 non-zero exit。
- `validate:full` 會執行 `validate-police-family` 與既有 `validate:police`。
- 新增 named police scanner 時必須有 positive / negative fixtures。
- advisory family 有 finding 時 validator 仍可 pass，但 `PoliceFamilyGateReport` 必須記錄。
- 新 police report 必須能進 ReviewAdvisory.machine-finding / HumanReviewQueue / follow-up-task route，不可繞過 HumanReviewDecision。

## 9. 風險與緩解

| 風險 | 緩解 |

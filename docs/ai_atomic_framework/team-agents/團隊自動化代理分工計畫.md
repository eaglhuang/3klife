# 團隊自動化代理分工計畫

Generated: 2026-05-26
Planning repo: 3KLife
Target framework: AI-Atomic-Framework / ATM
Status: planning source of truth

## 1. 目標與背景

ATM 目前已經有 Fast、Normal、Batch 三種治理通道，也有 task direction lock、batch checkpoint、evidence、pre-tool / pre-commit / CI 這些治理層。不過實戰中可以看到一個明顯問題：任務不是只有「改程式」一件事。AI 同時要讀文件、判斷 scope、寫程式、跑 validator、整理 evidence、處理 sandbox、最後 checkpoint / commit。這些工作全塞給同一個 agent，容易慢、容易漏、也容易偏移。

Team Agents 的目標是把一張任務卡變成一個小型施工現場：每個 agent 各司其職，但權限由 ATM 配置與檢查。它不是只服務 batch mode。Fast 小改、Normal 單張任務、Batch 多張任務都可以使用 team，只是 team 規模不同。

這份文件定義 ATM Team Agents 的規劃真相來源。它先作為設計文件，不直接修改 ATM framework source。後續若要實作，應從本文件拆出 `TASK-TEAM-*` 任務卡，並使用 ATM task-card-authoring 合約格式開卡。

### 大白話定位

- ATM 原本管「這次工作可不可以做、做完怎麼驗收」。
- Team Agents 管「這次工作中誰可以做哪一件事」。
- Team Agents 是加速層，不是放寬層。
- Team Agents 是治理合約，不綁定某一家 AI 編輯器或模型。

## 2. 核心設計原則

1. **Coordinator 唯一主控**
   - 只有 Coordinator 可以推進 ATM lifecycle。
   - 只有 Coordinator 可以 close / checkpoint / advance batch。
   - 只有 Coordinator 可以 git commit。

2. **寫入型權限是唯一裝備**
   - 同一組 active team 中，`git.write`、`task.lifecycle`、`file.write`、`database.write`、`pipeline.write`、`ci.write` 等寫入型權限同時只能給一個 agent。
   - 權限可以轉交，但必須經過 ATM lease/release 紀錄。

3. **讀取與驗證可以平行**
   - Reader、Scope Guardian、Validator、Evidence Collector 可以平行工作。
   - 但它們不能偽造 evidence，也不能把失敗 validator 包裝成 pass。

4. **語言 agent 可替換**
   - TypeScript 任務可使用 `implementer-typescript`。
   - Python 任務可使用 `implementer-python`。
   - C# / Cocos / data pipeline / DB migration 任務可以換成對應 agent。
   - 任務選用哪個 implementer 由 task metadata、repo probe、scopePaths、language hints 決定。

5. **Team 不取代 Fast / Normal / Batch**
   - Fast / Normal / Batch 決定任務治理通道。
   - Team 決定同一個治理通道內的角色分工。

6. **Team 不能繞過 ATM gate**
   - `allowedFiles`、evidence、validator、closure packet、batch checkpoint 仍然有效。
   - Team Agents 只協助更快完成這些要求。

7. **沒有 subagent runtime 也要可用**
   - v1 可以先輸出 team checklist，由同一個 AI 依角色執行。
   - 未來有 subagent adapter 時，再真正 spawn read-only / validator / evidence helper。

## 3. 角色分工

| Role | 中文定位 | 可做 | 不可做 | 常見權限 |
|---|---|---|---|---|
| Coordinator | 工地主任 / 主控代理 | 決定流程、啟動 team、分派權限、checkpoint、commit、handoff | 不應直接大量改程式，除非沒有 implementer | `task.lifecycle`, `git.write`, `evidence.write` |
| Reader / Planner | 文件閱讀員 | 讀 task card、計畫書、source、整理摘要 | 不改 source、不關任務 | `file.read` |
| Scope Guardian | 範圍守門員 | 檢查 allowedFiles、deliverables、scope amendment、跨 batch 衝突 | 不改 lock、不手改 `.atm/runtime` | `file.read` |
| Implementer | 實作者 | 依 allowedFiles 修改 source / docs / scripts | 不提交、不 checkpoint、不改 ATM runtime | `file.write` |
| Validator | 驗證員 | 跑 focused validators、typecheck、cache、回傳 command hash | 不把 fail 說成 pass | `exec.validator` |
| Evidence Collector | 證據整理員 | 整理 commandRuns、artifact paths、stdout/stderr hash、evidence draft | 不捏造 evidence、不關 task | `file.read`, optional `evidence.write` draft |
| Data Pipeline Agent | 資料管線員 | 產生資料管線 artifact、跑資料轉換 | 未授權不可寫正式資料 | `pipeline.write` |
| DB / Container Agent | DB/容器寫入員 | 寫 DB、容器、索引、外部狀態 | 未授權不可接觸外部資料庫 | `database.write` |
| CI Agent | CI 操作員 | 觸發 CI、讀 CI 結果、必要時更新 CI config | 未授權不可改 workflow | `ci.write` |
| Web Research Agent | 查詢員 | 查 web、下載文件、取得外部版本資訊 | query 與 download 權限分開 | `web.query`, `web.download` |

## 4. 權限裝備模型

Team permissions 分成兩種：

- `exclusive`：同一個 active team run 內只能有一個 owner。
- `shareable`：可多人使用，但仍可限制 scope。

### 權限目錄草案

| Permission | Mode | Scope | 預設 owner | 說明 |
|---|---|---|---|---|
| `task.lifecycle` | exclusive | task/batch | Coordinator | close/checkpoint/advance/release |
| `git.write` | exclusive | repo | Coordinator | stage/commit/tag/push 類寫入 |
| `file.read` | shareable | path/glob | Reader/Scope/Validator | 讀文件與 source |
| `file.write` | exclusive | path/glob | Implementer | 寫 source/docs/scripts/artifacts |
| `web.query` | exclusive | domain/policy | Web Research Agent | 查詢網路資料 |
| `web.download` | exclusive | domain/path | Web Research Agent | 下載外部資料或套件 |
| `exec.validator` | shareable | command allowlist | Validator | 跑不改 source 的驗證命令 |
| `exec.mutating` | exclusive | command allowlist | Coordinator 或專門 agent | 會改 repo/環境的指令 |
| `sandbox.write` | exclusive | environment config | Coordinator | 改 sandbox / temp root / 權限設定 |
| `pipeline.write` | exclusive | data pipeline path | Data Pipeline Agent | 寫資料管線輸出 |
| `database.write` | exclusive | DB/container target | DB Agent | 寫外部 DB、索引、容器 |
| `ci.write` | exclusive | CI provider/repo | CI Agent | 觸發或修改 CI |
| `evidence.write` | exclusive | task evidence | Coordinator | 寫正式 ATM evidence |

### 不可放寬規則

- `.atm/runtime/**` 不可由 team agent 手工編輯。
- `.atm/history/task-events/**` 不可手工編輯。
- `git.write` 不可給 Implementer。
- `task.lifecycle` 不可給非 Coordinator。
- `file.write` 必須是 task `targetWork.allowedFiles` 子集。
- `database.write`、`ci.write`、`web.download` 必須顯式授權，不可由預設 recipe 偷開。

## 6. Fast / Normal / Batch 使用方式

### 6.1 Fast

Fast 是小改入口，team 應該保持很薄。

建議 team：

- Coordinator
- Scope Guardian
- Validator

行為：

- 不預設啟動 Implementer subagent。
- `file.write` 通常由 Coordinator 持有。
- 超過 Fast 限制時升級 Normal。

### 6.2 Normal

Normal 是單張任務卡的標準施工現場。

建議 team：

- Coordinator
- Reader / Planner
- Scope Guardian
- Implementer
- Validator
- Evidence Collector

行為：

- Reader 先摘要任務合約。
- Scope Guardian 先檢查 deliverables 是否都在 allowedFiles。
- Implementer 只改 allowedFiles。
- Validator 可平行跑 focused checks。
- Evidence Collector 整理 commandRuns draft。
- Coordinator 最後 close/commit。

### 6.3 Batch

Batch 是多張任務卡的佇列治理，不代表多個 Implementer 同時改同一份 source。

建議 team：

- Batch Coordinator
- Current-task mini team
- Read-only preview agents for next task

行為：

- 同一時間只有 current queue head 的 Implementer 可持有 `file.write`。
- 下一張卡的 Reader 可提前讀，但不可寫。
- Validator 可針對不衝突的靜態檢查預熱 cache。
- Evidence Collector 可整理草稿，但正式 evidence write 仍由 Coordinator 執行。

## 7. 安全規則

1. **Exclusive permission uniqueness**
   - 同一 teamRun 中，每個 exclusive permission 只能有一個 owner。

2. **No manual runtime edit**
   - 任何 agent 都不可手改 `.atm/runtime/**`。
   - scope amendment 必須走 CLI。

3. **Write scope must be bounded**
   - `file.write` lease 必須指定 paths。
   - paths 必須是 task `allowedFiles` 子集。

4. **Coordinator-only lifecycle**
   - close / checkpoint / advance / commit 只能由 Coordinator 執行。

5. **Explicit external side effects**
   - web download、DB write、CI write、pipeline write、sandbox write 都必須顯式授權。

6. **Evidence cannot lie**
   - exitCode 非 0 的 validator 不能被標成 validation pass。
   - 可記錄為 diagnostic evidence，但不能算通過。

7. **Adapter failure cannot bypass governance**
   - 真 subagent runtime 失敗時，只能退回 manual-team checklist。
   - 不可直接改成無治理寫入。

8. **Team Agents 採用併發契約，不定義併發 primitive**
   - Team Agents 負責「誰可以在 team runtime 中讀、寫、驗證、交接」。
   - CID E2 / `TASK-CID-0005` 負責定義底層 `Active Resource Index` / `Scope Lease Registry`、`leaseEpoch`、fencing token、wait-for graph 與 stale holder 規則。
   - Team Agents 只能消費這些狀態做顯示、診斷與 validator；不可把它擴張成第二套 task scheduler、第二套 Git，或新的 claim / close 決策來源。

## 8. ATM Team Agents 可組合治理落地介面

本章把 Team Agents 從概念推進到 ATM 可實作介面。重點是：Team 是可組合、可配置、可驗證的 runtime contract，而不是聊天提示。

### 8.1 Team CLI 草案

建議新增 `team` command group：

```shell
node atm.mjs team plan --task <id> --json
node atm.mjs team start --task <id> --recipe <recipe-id> --actor <id> --json
node atm.mjs team status --team <teamRunId> --compact --json
node atm.mjs team lease --team <teamRunId> --agent <agentId> --permission <permissionId> --json
node atm.mjs team release --team <teamRunId> --agent <agentId> --permission <permissionId> --json
node atm.mjs team complete --team <teamRunId> --json
node atm.mjs team abandon --team <teamRunId> --reason "<reason>" --json
```

v1 預設順序：

1. `team plan`：只讀 task 與 config，回建議 team，不寫 runtime。
2. `team start`：建立 `.atm/runtime/team-runs/<teamRunId>.json`。
3. `team status --compact`：只回目前 task、agents、leases、下一步命令。
4. `team complete`：由 Coordinator 在 close/checkpoint 前標記 team 完成。

### 8.2 `next --claim` 整合

`next --claim` 不應自動 spawn team，但應回傳 team 建議：

```json
{
  "teamRecommendation": {
    "enabled": true,
    "required": false,
    "recipeId": "atm.default.normal.typescript",
    "startCommand": "node atm.mjs team start --task TASK-AAO-0005 --recipe atm.default.normal.typescript --actor codex-main --json",
    "reason": "This task has multiple deliverables and validators; a scoped task team can reduce evidence and validation overhead."
  }
}
```

如果 task card 明確宣告：

```yaml
team:
  required: true
  recipe: atm.default.normal.typescript
```

則 `tasks close` / `batch checkpoint` 前必須確認 team run 已完成，否則回：

```text
ATM_TEAM_COMPLETION_REQUIRED
```

### 8.3 Permission Validation 錯誤碼

Team 啟動與 lease 變更時，ATM 必須檢查權限唯一性與範圍合法性。

併發資料來源採「只讀消費」原則：Team runtime 可以讀取 CID E2 定義的 `Active Resource Index` / `Scope Lease Registry` 來呈現 active holder、lease epoch、wait-for dependency 與 potential conflict；但 Team Agents 不得藉此建立新的任務排程、queue promotion、claim、close 或 commit 決策。這些生命週期仍由 ATM `next` / task close / batch checkpoint 與 Coordinator-only lifecycle 控制。

建議錯誤碼：

| Code | 觸發情境 | requiredCommand |
|---|---|---|
| `ATM_TEAM_PERMISSION_CONFLICT` | 兩個 agent 同時持有同一 exclusive permission | 修改 recipe 或 release 其中一個 lease |
| `ATM_TEAM_WRITE_SCOPE_EXCEEDED` | agent 要寫入不在 lease paths 的檔案 | `team lease` 或 `tasks scope --add` |
| `ATM_TEAM_REQUIRED_PERMISSION_MISSING` | recipe 缺 lifecycle/git/evidence 等必要 owner | 補 recipe permission |
| `ATM_TEAM_UNIQUE_OWNER_REQUIRED` | `git.write` / `task.lifecycle` 沒有唯一 owner | 指派 Coordinator |
| `ATM_TEAM_AGENT_PROFILE_MISSING` | recipe 指到不存在的 agent profile | 安裝或改用 fallback profile |
| `ATM_TEAM_RUNTIME_NOT_AVAILABLE` | 要求真 subagent，但目前 adapter 不支援 | 改用 manual-team checklist |

### 8.4 Hook / Gate 整合

pre-tool：

- 如果 active team 存在，寫入工具必須對應目前持有 `file.write` lease 的 agent。
- 寫入路徑超出 lease 時，回 `ATM_TEAM_WRITE_SCOPE_EXCEEDED`。
- web download / DB write / CI write / sandbox write 必須檢查對應 permission owner。

pre-commit：

- 只有持有 `git.write` 的 Coordinator 可以 commit。
- staged files 若屬於 active team，commit evidence 必須帶 `teamRunId`。
- 非 Coordinator commit 回 `ATM_TEAM_GIT_OWNER_REQUIRED`。

`tasks close` / `batch checkpoint`：

- 如果 task 要求 team，closure packet 必須包含 team summary。
- summary 至少包含：agents、permission leases、write scope、validators、evidence handoff、teamRunId。

### 8.5 Team Runtime Adapter

Team Agents 不應綁死某一家 AI 編輯器或模型。ATM 只定義 adapter contract：

```ts
interface TeamAgentRuntimeAdapter {
  id: string;
  supportsSpawn: boolean;
  supportsReadOnlyAgent: boolean;
  supportsWriteScopedAgent: boolean;
  spawnAgent(input: TeamAgentSpawnRequest): TeamAgentSpawnResult;
}
```

沒有 adapter 時：

- `team plan` 仍可輸出角色 checklist。
- Coordinator 可以手動依角色執行。
- evidence 記錄 `executionMode: "manual-team"`。

有 adapter 時：

- Reader / Validator / Evidence Collector 可以平行 spawn。
- Implementer 必須先取得唯一 `file.write` lease 才能 spawn。
- Adapter 失敗不能自動降級成無治理寫入。

### 8.6 組合與替換策略

Team recipe 應允許用參數替換 agent：

```json
{
  "replace": {
    "implementer": "implementer-python"
  },
  "when": {
    "language": "python"
  }
}
```

替換規則：

- replacement agent 必須滿足原 role 的必要 permission。
- replacement agent 不可額外拿未授權 exclusive permission。
- 若 replacement 需要新增權限，例如 `pipeline.write`，task card 必須顯式宣告。
- fallback 可以降級成 generic implementer，但不能自動取得更寬 file scope。

### 8.7 Rollout 順序

實作時不要一次把 subagent、hook、runtime 全塞進去。建議漸進：

1. Schema + docs。
2. `team plan` dry-run。
3. `team start/status` runtime。
4. Permission lease validator。
5. Hook / pre-commit enforcement。
6. `next --claim` playbook integration。
7. closure packet team summary。
8. 真 subagent runtime adapter。

這個順序的好處是：前四步就能改善 AI 操作清晰度；最後一步才碰最複雜的多代理執行。
## 9. 里程碑

任務卡開卡順序改以里程碑為準，不再沿用早期草稿的 M1-M8 編號。每個里程碑都要先帶來可感的任務卡效果，再往 runtime 自動化推進。

## 13. 從無到有的最小落地路線

這一段定義的是「怎麼從 0 開始，先讓任務卡有感」，不是一口氣把所有 runtime 自動化一次做完。原則是先讓人類看得懂、能派工、能回報，再逐步加自動派隊與權限收斂。

### M0：先把文件與班底立起來

目標：

- 先定義角色名冊。
- 先定義派工單與回報單。
- 先讓每張 task 卡知道要交給誰、誰回報、誰收斂。
- 不改 ATM source，不做 runtime 自動派工。

交付物：

- `team-brief.md`
- `agent-report.md`
- `team-summary.md`
- `captain-decision.md`

### M1：每張任務卡先有最小小隊

目標：

- 讓每張任務卡都有一個可工作的最小班底。
- 小卡先從 2 到 3 人開始。
- 隊長先能派工，不必等完整 runtime。

建議最小班底：

- `Task Captain`
- `Atomization Planner`
- `Code Builder`
- `Check Runner`

### M2：把回報文件做成固定格式

目標：

- 每個 agent 都回同一種格式的報告。
- 隊長可以快速彙整，而不是逐段讀聊天紀錄。

交付物：

- `agent-report.md`
- `team-summary.md`
- `team-memory-shard.md`

### M3：讓隊長真的能做決策

目標：

- 隊長可以決定要不要加副隊長。
- 隊長可以決定要不要拆 phase。
- 隊長可以決定這張卡是否先停下來做 preflight。

### M4：加入原子化規劃

目標：

- 每張任務卡都先經過 Atomization Planner。
- 每張任務都要先問一次：這張卡的 primary atom 是什麼？
- 若牽涉大腳本、跨 capability 或需要改 atom map，先提示，不要直接硬做。

### M5：加入權限與 team run

目標：

- 讓隊員拿到明確的 lease。
- 讓不同角色只能碰自己被授權的路徑與權限。
- 把 team run、permission lease、handoff 變成可追蹤資料。

### M6：加入 Atomic Police Agents

目標：

- 把原子警察做成固定巡邏角色。
- 支援每日中午巡邏、claim 前巡邏、close 前巡邏、batch checkpoint 前巡邏。
- 巡邏報告可直接給人類看。

### M2 完成後的「90 分鐘第一張卡」承諾

M2 收口後，ATM 對新採用者要兌現一個可量化的承諾：**從 git clone 到第一張卡 close 並產生 closure-packet + patrol-report，總時間不超過 90 分鐘**。這個承諾的存在理由是補上 7-Agent Factory 在「明確時長 + 開箱即用範例」這兩件事上對 ATM 仍有的優勢；M2 把所有必要範本與 validator 落地後，這條時間線就有了客觀可驗證的底盤。

承諾的時間切片：

| 分鐘區間 | 採用者實際看到的事 | 由哪張卡兌現 |
|---|---|---|
| 0-15 | `npx create-atm my-app --agent claude-code` 完成；`node atm.mjs doctor --json` 全綠 | 既有 |
| 15-30 | 複製 `examples/team-agents-minimal/team-brief.md`，改 4 個 allowedFiles 欄位、改 task 標題 | TASK-TEAM-0004 |
| 30-60 | `node atm.mjs next --prompt "..."` → Agent claim → 改 1 個小檔 → `npm run typecheck` 綠 | 既有 + TASK-TEAM-0002/0003 |
| 60-80 | `node --strip-types scripts/validate-team-agents-templates.ts` 綠；agent-report.md 寫好 | TASK-TEAM-0004/0005 |
| 80-90 | `node atm.mjs tasks close --json` → closure packet 寫入；產出第一份 patrol-report.md | TASK-TEAM-0006 + 既有 closure pipeline |

驗收這個承諾的方式：M2 三張卡全部 done 後，至少做一次 wall-clock dry run，由 M2 收口前未接觸過 ATM 的觀察者執行，全程未超過 90 分鐘即為通過。dry run 結果寫進 `examples/team-agents-minimal/QUICK_START_WALK_THROUGH.md`。

### examples/team-agents-minimal/ 落點與內容範圍

為了讓上述承諾真的能被新採用者「複製貼上」，M2 必須在 framework repo 種下一個範例目錄。建議落點與內容範圍如下，由 TASK-TEAM-0004 起頭、TASK-TEAM-0005/0006 各自補一份範例檔：

```
AI-Atomic-Framework/
└── examples/
    └── team-agents-minimal/
        ├── README.md                    # 90 分鐘走完流程的入口；列出 5 個區間
        ├── team-brief.md                # 0004 落地；新採用者只改 4 個欄位
        ├── agent-report.md              # 0004 落地；空白範本
        ├── team-summary.md              # 0004 落地；空白範本
        ├── captain-decision.md          # 0005 落地；空白範本
        ├── team-memory-shard.md         # 0005 落地；附一條範例 lesson
        ├── patrol-report.md             # 0006 落地；附一條範例 finding
        └── QUICK_START_WALK_THROUGH.md  # 至少一次 dry run 的逐分鐘紀錄
```

範例目錄的設計原則：

- 所有檔案都是 plain Markdown，不引入新的 schema。
- 範例值（task id, allowedFiles, owner）使用 `EXAMPLE-` 前綴或註解標示「請改成你自己的」。
- 不引入 `.atm/` runtime 檔——範例不模擬實際 ATM state，只示範文件流。
- 範例值不可被 `validate-neutrality-scanner.ts` 標為 protected-surface 違規。
- 採用者複製整個目錄到自己的 repo 後，應該不需要再讀計畫書即可動手。

這個範例目錄是 ATM 對「Factory 開箱即用儀式感」的回應：你不必懂 27 個 packages 與 9 個警察家族，只要懂 6 個範本檔加 4 個欄位的 task 卡，就能跑完第一條治理鏈並看到證據包。

## 15. Agent 名冊與職責

### `Task Captain`

職責：

- 決定小隊大小。
- 決定是否需要副隊長。
- 決定任務是否可以進入實作。
- 決定是否 close-ready。

禁區：

- 不可繞過 ATM gate。
- 不可讓隊員超出 allowedFiles。
- 不可用口頭結論代替 evidence。

### `Task Lieutenant`

職責：

- 任務太複雜時協助隊長拆 phase。
- 追 blocker。
- 協助整理跨 agent 依賴。

### `Atomization Planner`

職責：

- 每張任務卡開工前先做 atom/map 化規劃。
- 判斷 primary atom、related atoms、capability touched、command surface。
- 檢查是否需要更新 path-to-atom-map。
- 檢查是否有大腳本風險，是否該先拆小。

禁區：

- 不直接改 source。
- 不自行 claim / close。
- 不替 Implementer 做 code change。

### `Scope Sentinel`

職責：

- 檢查 allowedFiles。
- 檢查 dirty tree。
- 檢查 claim overlap。
- 檢查是否需要拆 task。

### `Code Builder`

職責：

- 依派工單實作。
- 只碰被授權的檔案。
- 做完回報，不自行 close / commit。

### `QA Lead` 與 `Check Runner`

職責：

- 決定要驗什麼。
- 跑 validators。
- 把 pass / fail / diagnostic 分清楚。

### `Evidence Curator`

職責：

- 整理 command-backed evidence。
- 收 commandRuns、artifact、hash、validator 摘要。
- 幫隊長快速做 closure packet。

### `Closure Steward`

職責：

- 結案前檢查 closure packet、ledger、events、git-head。
- 確認是否可安全 close。

### `Atomic Police Agents`

職責：

- 固定巡邏。
- 盤查規則。
- 輸出摘要報告。
- 不直接改 source。

可用角色：

- `Scope Police`
- `Evidence Police`
- `Ledger Police`
- `Atom Map Police`
- `Encoding Police`
- `Runner Sync Police`

## 17. 隊長決策模型與任務卡重排原則

### 隊長決策模型

- 隊長必須在派 `Code Builder` 前先取得 `Atomization Planner` 結論。
- 碰到 `tasks.ts`、`next.ts`、`evidence.ts`、`hook.ts` 這類大腳本時，原子規劃師不可省略。
- 超過 2 個核心檔、跨 repo、涉及 git / evidence / closure、或大於 600 行腳本時，建議加入副隊長。
- `map update needed: yes` 時，隊長要先確認 task allowedFiles 是否包含 atom map。
- `task split needed: yes` 時，先停 coding，回報人類或開新卡。
- 隊長不可繞過 ATM gate，不可讓隊員超出 allowedFiles，不可用口頭 pass 代替 evidence。

### 任務卡重排原則

- 任務卡的開卡順序應以里程碑為準，不以舊的編號順序為準。
- 如果既有 task 卡順序和里程碑順序不一致，優先重排，不要硬沿用錯誤順序。
- 如果一張卡的內容已偏離當前里程碑，重開新卡通常比沿用舊卡安全。
- 建議開卡順序：
  - 先開 M0 文件與名冊卡
  - 再開 M1 最小小隊卡
  - 再開 M2 回報格式卡
  - 然後才進 M3-M6 的 runtime、lease、巡邏擴充

## 18. Atomic Police Agents 巡邏隊

### 定位

- 原子警察是固定巡邏型 agent。
- 預設 read-only，只巡檢、報告、建議，不直接改 source。

### 常見巡邏時機

- 每日中午巡邏
- 任務 claim 前巡邏
- 任務 close 前巡邏
- batch checkpoint 前巡邏
- 大腳本改動前巡邏

### 常見巡邏隊

- `Daily Noon Patrol`
- `Close Gate Patrol`
- `Big Script Patrol`
- `Multi-Agent Collision Patrol`
- `Ledger Consistency Patrol`
- `Runner Sync Patrol`

### 巡邏報告

- 巡邏結果輸出成 `patrol-report.md`。
- 報告要能讓人類一眼看懂哪裡有風險、要不要繼續、下一步該做什麼。
- 巡邏隊如果發現風險，應該建議任務卡，而不是偷偷改 source。

### 巡邏隊能帶來的效果

- 提前抓出 scope 衝突。
- 提前抓出 evidence 不完整。
- 提前抓出 ledger / events 不一致。
- 提前抓出大腳本風險與 atom map 缺口。
- 讓人類知道自動巡邏真的做了什麼。

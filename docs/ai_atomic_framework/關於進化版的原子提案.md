## 三層防護模型（推薦方案）

Hash-lock 和原子化各有適用場景。最穩健的方案是分層防護：

### Layer 1 — 不可變核心（Constitutional Immutables）→ 只用 Hash-lock

這一層定義「什麼是原子」。它本身不能是原子（否則誰來治理治理者？）。

| 組件 | 保護機制 | 理由 |
|---|---|---|
| `schemas/atomic-spec.schema.json` | hash-lock + schema version | 改這個等於改原子的定義本身 |
| `schemas/registry.schema.json` | hash-lock + schema version | registry 是所有原子的真相索引 |
| `schemas/regression-matrix.schema.json` | hash-lock + schema version | regression 是品質閘門的契約 |
| Hash-lock 演算法本身 | 只能透過 schema migration ceremony 更改 | 改 hash 演算法 = 所有現有 hash 失效 |

**修改方式**：不能 patch——必須 **版本遷移**（atmSchemaVersion bump + migration script + 全 registry 重算 hash）。這相當於「修憲程序」。

### Layer 2 — 自治原子（Self-Governed Atoms）→ Hash-lock + 原子化治理

這一層是框架的可演化部分。它們本身就是原子，用 ATM 的治理流程管理自己。

| 組件 | Atom ID | 狀態 | Hash-lock | 原子化治理 |
|---|---|---|---|---|
| Seed (core bootstrap) | ATM-CORE-0001/0002（`logicalName: atom.core-seed`） | ✅ governed | ✅ 三段 hash | ✅ `atm verify --self` |
| neutralityScanner | ATM-CORE-0003（`logicalName: atom.plugin-rule-guard.neutrality-scanner`） | ⏳ 計畫中 | 計畫中 | 計畫中 |
| Police plugin rules | 計畫中 (ATM-2-0005) | ⏳ | 計畫中 | 計畫中 |
| Registry manager | 計畫中 (ATM-2-0004) | ⏳ | 計畫中 | 計畫中 |
| CLI commands | 已建立 (ATM-1-0004) | 待收編 | 待補 | 待補 |
| Adapter interfaces | 已建立 (ATM-1-0005/6) | 待收編 | 待補 | 待補 |

**修改方式**：走 ATM 標準流程——spec 更新 → hash 重算 → regression 驗證 → registry 更新。任何 hash drift 都會被 `atm verify --self` 攔截。

### Layer 3 — 可變配置（Mutable Configuration）→ 標準版本控制

這一層是消費者自訂的部分，不適合原子化。

| 組件 | 保護機制 | 理由 |
|---|---|---|
| `.atm/profile` | git + task-lock | 每個專案不同；原子化開銷不值得 |
| Adapter 設定 | git + schema validation | 配置隨宿主專案變化 |
| Bootstrap templates | git + hash 校驗（輕量） | 快速迭代中，全原子化太重 |

---

## 為什麼不能只用 Hash-lock？

Hash-lock 解決的是「完整性偵測」（THAT something changed），但它不解決：

| 問題 | Hash-lock 能解決？ | 原子化治理能解決？ |
|---|---|---|
| 有人改了一行程式碼 → 偵測到 | ✅ | ✅ |
| 判斷這個改動是否合法 | ❌ | ✅（spec / regression / police） |
| 自動回退到上一個已知好的版本 | ❌ | ✅（registry 有版本歷史） |
| 確保改動不破壞下游消費者 | ❌ | ✅（regression matrix） |
| 追蹤誰、何時、為何改動 | ❌（只知道 hash 不同） | ✅（evidence / artifact / log） |

**Hash-lock 是必要但不充分的。** 它是原子化治理的基礎設施之一，不是替代方案。

## 為什麼不能全部原子化？

有些東西不能是原子——因為它們定義了「什麼是原子」。如果核心 schema 本身也是原子，就產生循環依賴：

```
原子需要 atomic-spec.schema.json 才能被驗證
atomic-spec.schema.json 如果是原子，就需要自己來驗證自己
→ 自驗證悖論
```

ATM-1.5 用一個巧妙的方式部分解決了這個悖論：seed 用自己的 spec 描述自己（ATM-CORE-0001），然後由 ATM-CORE-0002 接管治理。但核心 **schema 本身**仍然在原子系統之外——它是「憲法」，不是「法律」。

---

## 結論與建議

| 方案 | 適用場景 | 可行性 | 推薦度 |
|---|---|---|---|
| 只用 Hash-lock | ❌ 不足——偵測到變化但無法治理演化 | 技術可行但不完整 | ⚠️ 僅作為基礎層 |
| 全部原子化 | ❌ 不可能——核心 schema 存在自驗證悖論 | 結構性不可行 | ❌ |
| **三層防護（推薦）** | ✅ 不可變核心 + 自治原子 + 可變配置 | ✅ 完全可行，ATM-1.5 已是實證 | **✅ 推薦** |

**ATM 已經在正確的路上。** ATM-1.5 phase 完成了自舉悖論的第一輪化解（seed 用自己描述自己、hash-lock 自我驗證、governed 收編）。接下來的路線圖自然地延伸這個模型：

1. **alpha0 後**：hash-lock 核心 schemas（Layer 1 就位）
2. **alpha1 中**：CLI、adapters、police rules 收編為原子（Layer 2 擴展）
3. **alpha1 後**：框架演化完全透過 ATM 標準流程管理（Layer 2 全覆蓋）

不需要新增任何機制——現有的 hash-lock + atom spec + registry + `atm verify --self` 已經構成完整的三層防護基礎。缺的只是把更多組件收編進 registry（ATM-2 phase 的自然工作）。

## 命題 1：原子版號 + 不退轉保證 + Rollback

### 現有基礎設施（已建成）

```
atomic-spec.schema.json
  └─ hashLock: { specHash, codeHash, testHash }  ← ATM-1-0003 已定義

atomic-registry.json
  └─ ATM-CORE-0001: { specHash: ok, codeHash: ok, testHash: ok }  ← ATM-1.5-0002 已實作

atm verify --self  ← 修改任何一行即偵測 drift  ← ATM-1.5-0002 已驗證

test-report.schema.json  ← ATM-2-0003 已建立；test runner 產出 JSON report

ATM-2-0004 Registry + HashLock MVP  ← 正在實作中
```

### 缺少的三塊拼圖

**1. Version History（版本歷史陣列）**
目前 registry 只記錄 CURRENT hash，沒有前版紀錄。

```jsonc
// 現在的 registry entry
{ "atomId": "ATM-CORE-0001", "logicalName": "atom.core-seed", "specHash": "abc123", "codeHash": "def456" }

// 需要的結構
{
  "atomId": "ATM-CORE-0001",
  "logicalName": "atom.core-seed",
  "currentVersion": "1.1.0",
  "versions": [
    { "version": "1.0.0", "specHash": "abc123", "codeHash": "def456", "testHash": "ghi789", "timestamp": "..." },
    { "version": "1.1.0", "specHash": "xxx000", "codeHash": "yyy111", "testHash": "zzz222", "timestamp": "..." }
  ]
}
```

**建議時機**：ATM-2-0004（正在 in-progress）的自然延伸，或緊接其後的 follow-up 卡。

**2. Non-regression Gate（不退轉閘門）**
版本升級時，新版 v1.1 必須通過 v1.0 的所有 test fixtures + v1.1 新增的 tests。

```
atm upgrade <atom-id> --from v1.0 --to v1.1
  Step 1: 跑 v1.0 的 regression fixtures against v1.1 code → 必須全綠
  Step 2: 跑 v1.1 的新 tests → 必須全綠
  Step 3: 比較 test coverage → v1.1 >= v1.0
  Step 4: 計算新 hashLock → 寫入 registry
```

**建議時機**：ATM-2-0005（Police plugin API）+ ATM-2-0004（Registry）組合。

**3. Rollback Command（回退指令）**

```
atm rollback <atom-id> [version]
  Step 1: 從 versions[] 取出目標版本的 hashLock
  Step 2: 還原 spec/code/test 到該版本（透過 git checkout 或 artifact store）
  Step 3: 驗證 hashLock 一致
  Step 4: 更新 registry currentVersion
```

**建議時機**：ATM-2-0004 完成後立即可建，因為 version history 和 rollback 是同一個 registry 擴充。

### 可行性結論

✅ **完全可行**。三塊拼圖都建立在已有基礎上（spec schema 有 hashLock 預留、test runner 已產 JSON report、registry 正在建構中）。不需要新的抽象概念，只需在 ATM-2-0004/0005 的自然工作中擴充。

## 命題 3：自我回饋進步迴圈（最重要的創新）

### 使用者的核心構想

```
Atom v1.0 ──→ 生產環境使用 ──→ 收集回饋/品質證據
                                        ↓
                               提議新版本 v1.1
                                        ↓
                         驗證機制證明品質是否進步
                                        ↓
                    品質警察自動審查 + 人類審核清單
                                        ↓
                     通過 → 升級到 v1.1；不通過 → 保留 v1.0
```

這本質上是把原子的生命週期從「單次交付」延伸為「持續演化」，且演化由**證據驅動**而非**意願驅動**。

| 回饋收集 | ATM-2-0009 Artifact/Evidence Store | ⏳ schema 計畫中 |
| 品質證據 | `test-report.schema.json` (ATM-2-0003) | ✅ 已建 |

| 人類審核清單 | **尚未規劃** | ❌ 需新增 |

在 ATM-2-0005（Police plugin）中建立：

```
atm upgrade <atom-id> --propose v1.1
  Step 1: Non-regression check（v1.0 tests 全過）

    - v1.1 coverage >= v1.0 coverage ？
    - v1.1 handles v1.0 documented edge cases ？
  Step 3: New capability proof（v1.1 新 tests 全過）
  Step 4: 產出 upgrade-proposal.json
```


# Part V：原子與原子地圖識別體系與行為分類學

> 產出日期：2026-05-07

> 範圍邊界：alpha1 範圍；不阻塞 alpha0 critical path（ATM-2-0012 + ATM-2.5-0002）

## §1 識別五層模型

ATM 把「一個原子是什麼」區分為五層識別，每層各司其職、不互相替代：

| 層 | 名稱 | 範例 | 用途 | 現況 |
|---|---|---|---|---|
| L1 | **Logical ID（命名空間）** | `atom.h2u.normalize-css-color`、`map.h2u.css-pipeline` | 人類可讀識別、namespace 路由 | ✅ 原子已有；地圖 ATM-2-0023 規劃中 |
| L2 | **Fully-Qualified ID (FQID)** | `atom.h2u.normalize-css-color@1.2.0` | 跨版本引用、registry 索引鍵 | ✅ atomVersion 已有 |
| L3 | **Content Hash（三段 hash）** | `specHash / codeHash / testHash`、`mapHash` | 完整性偵測、drift 警報 | ✅ 已實作 |
| L4 | **Semantic Fingerprint（語意指紋）** ⭐ NEW | `sf:sha256:...` | 去重警察主要輸入；由 spec inputs/outputs/contract 經 normalization 後 hash | ❌ ATM-2-0026 引入 |
| L5 | **Lineage Tag（系譜標記）** ⭐ NEW | `bornBy: atomize / split / extract / ...` + `parentRefs` | 追蹤誰生出誰、回滾與審計 | ❌ ATM-2-0026 引入 |

**為什麼五層都需要**：

| 場景 | 必須使用的層 |
|---|---|
| 「這個原子是哪一個？」 | L1 |
| 「我要呼叫哪個版本？」 | L2 |
| 「這個檔案被改過嗎？」 | L3 |
| 「這個原子和那個原子是不是做一樣的事？」 | **L4** |
| 「這個原子是怎麼生出來的？」 | **L5** |

L1+L2+L3 解決識別與完整性；L4+L5 解決去重與系譜，缺一不可。

### §1.1 Canonical ID 與派生 URN

2026-05-08 補強：外部系統與跨 repo exchange 可以使用 URN 風格位址，但 URN **不是第六種主鍵**，也不能取代 ATM 既有 canonical ID。

| 層級 | 真相來源 | 可寫入 registry？ | 範例 |
|---|---|---|---|
| Atomic ID | `atomId` / `mapId` | ✅ 唯一可寫主鍵 | `ATM-CORE-0001`、`ATM-MAP-0001` |
| Derived URN | 由 canonical ID + version 推導 | ❌ 只作查詢 / exchange / log ref | `urn:atm:atom:ATM-CORE-0001@1.0.0` |

格式固定為：

```text
urn:atm:<nodeKind>:<canonicalId>[@<semver>]
```

- `nodeKind` 只能是 `atom | map | police | behavior`；其中 `atom` 與 `map` 必須能無損轉回 canonical `atomId` / `mapId`。
- `canonicalId` 仍使用 `ATM-{bucket}-{NNNN}` 或 `ATM-MAP-{NNNN}`；禁止新建 `urn:atm:*` 後再反推不同 ID。
- `@version` 可省略；省略時 resolver 讀 registry current pointer / entry currentVersion。
- registry hot path 不另存 URN 欄位；如需外部引用，由 `formatAtmUrn()` 派生，避免第二套識別漂移。

此規則由 `ATM-2-0047` 實作 URN resolver 與 RegistryIndex façade 承接。

## §2 為什麼 Map ID 不用「first+last atom」

直覺上把 map 命名為「第一個原子 ID + 最後一個原子 ID」很方便，但有結構性問題：

| 問題 | 原因 |
|---|---|
| 多入口 / 多出口 map 沒有「最後一個」 | DAG 可有多個 leaf node |
| 成員順序變動 ID 就改 | 不穩定，無法當 registry 主鍵 |
| 不同 map 可能撞 first/last | 中間段不同卻撞 ID |
| 演化時 first/last 換掉 → ID 改變 | 跟 versionHistory 無法對齊 |

**正確切法**：把這個直覺從「ID」改放到「fingerprint」：

- **mapId**（穩定）：人類給的 logical ID，例如 `map.h2u.css-pipeline`
- **mapHash**（隨內容變）：成員 + 邊 + entrypoints 的 hash
- **mapSemanticFingerprint** ⭐ NEW：基於 entrypoint input/output 與 map-level qualityTargets 的 hash（不含內部成員，純行為指紋）

## §3 Semantic Fingerprint 計算規範

**對於原子（atomSemanticFingerprint）**：

```
canonicalSpecForFingerprint = {
  inputs:  sortByName(spec.inputs.map(p => ({ name, kind, required }))),
  outputs: sortByName(spec.outputs.map(p => ({ name, kind, required }))),
  language: { primary: spec.language.primary },         // 不含 sourceExtensions / tooling
  validation: { evidenceRequired: spec.validation?.evidenceRequired ?? false },
  performanceBudget: spec.performanceBudget ?? null,
  // 排除：id, title, description, hashLock, dependencyPolicy, runtime, adapterRequirements, tags
}
sf = "sf:sha256:" + sha256(canonicalize(canonicalSpecForFingerprint))
```

**對於地圖（mapSemanticFingerprint）**：

```
canonicalMapForFingerprint = {
  entrypoints: sortByName(map.entrypoints),
  qualityTargets: map.qualityTargets,
  // 排除：mapId, mapVersion, members[], edges[], mapHash
}
sf = "sf:sha256:" + sha256(canonicalize(canonicalMapForFingerprint))
```

**用途**：

- 兩個原子 sf 完全相同 → 100% 規格重複（強去重候選）
- sf 部分相同（只 inputs 同 / 只 outputs 同）→ 弱重複，police 呼叫 LLM skill 算 90%+ 行為相似度
- sf 不同 → 不視為重複（即使 atomId 命名相似）

## §4 性能與記憶體：hot/cold 分離 + sublinear lookup

當原子數量達到 10K~100K 等級時，schema 設計必須讓 registry hot-path 維持 O(1) 索引、避免每次 lookup 都 deserialize 大量欄位。

### §4.1 設計原則

| 原則 | 落實方式 |
|---|---|
| Hot path 欄位最小化 | registry entry 只保 `atomId / atomVersion / status / hashLockDigest / semanticFingerprint / locationRef` |
| Lineage / TTL / Evidence refs 不放主 entry | 移到 `lineage-log/<atomId>.json`、`evidence-index/<atomId>.json`，主 registry 只放 URI ref |
| Semantic fingerprint 直接是 64-char hex string | 無需 nested object；可直接作 hash table key |
| Registry sharding 已有規範 | `registry.schema.json` 的 `sharding` 已定義 single-document / external-parts，不再新增 |
| 不在 registry 重複 spec 內容 | 用 `specPath` 引用 |
| 多形原子不展開實例 | template 與 param-spec 各自一份；實例化結果不寫進 registry |
| Behavior history 限長 | 每個 atom 的 `parentRefs` 只保「直接父」；完整歷史走 lineage-log |

### §4.2 Hot vs Cold 分離示意

```
registry.json (hot, < 10MB even at 100K atoms)
└─ entries[].
   ├─ atomId             (短字串)
   ├─ atomVersion        (短字串)
   ├─ status             (enum)
   ├─ hashLockDigest     (64-char hex)
   ├─ semanticFingerprint(64-char hex)  ← 直接 string，不是 object
   ├─ locationRef        ("workbench:atomic_workbench/atoms/<id>/")
   ├─ lineageLogRef      ("logs:lineage/<id>.json")     ← 只放 URI
   └─ evidenceIndexRef   ("logs:evidence/<id>.json")    ← 只放 URI

lineage/<atomId>.json (cold)
└─ history[].{ bornBy, parentRefs, bornAt, mutatedAt, behaviorRunId }

evidence/<atomId>.json (cold)
└─ refs[].{ evidenceType, path, generatedAt }
```

### §4.3 Schema 設計守則

1. registry hot entry 的欄位數 **≤ 10**
2. 所有 array 欄位都不能無上限——若超過上限就強制改用外部 ref
3. Optional / additive 欄位用 nullable string 或省略，不要複雜 nested optional object
4. `compatibility` 等子物件最多 nest 2 層
5. semantic fingerprint 必須能用 32-bit / 64-bit prefix 做 sublinear lookup（dedup police 不可 O(n²) 全比對）

### §4.4 Dedup Police 的索引策略

- 透過 RegistryIndex 維護 `fingerprint-index`：`Map<sf-prefix-16chars, nodeRef[]>`
- 偵測新原子時，先 sf prefix lookup（O(1)），命中後再做完整比對
- 跨 100K atoms 的 sf 全掃必須在數百毫秒內完成；ATM-2-0030 acceptance 包含此 budget

### §4.5 跨系統比對 fast-path：version-index

當兩套高度原子化的系統互相比對原子（判斷哪些共用、哪些需同步升版），若每次都走完整 sf 計算再比對，成本過高。版本號碼本身是高效的 fast-path filter。

**version-index 結構**（與 fingerprint-index 平行）：

```jsonc
// version-index.json
{
  "atom.h2u.normalize-css-color": {
    "latest": "1.2.0",
    "versions": ["1.0.0", "1.1.0", "1.2.0"]
  }
}
```

**跨系統原子比對三層 fast-path**：

| Step | 比對方式 | 結果 | 成本 |
|---|---|---|---|
| 1 | atomId hash lookup | 找到 → Step 2；找不到 → 走 sf 比對 | O(1) |
| 2 | version semver compare | 版本相同 → MATCH；major 不同 → INCOMPATIBLE | O(1) |
| 3 | sf 比對 | sf 相同 → 行為等價；sf 不同 → 真正不相容 | O(1) per atom |

**性能效益**：在兩系統 80%+ atoms 同步的常見情境下，Step 1+2 即可解決大部分比對，避免不必要的 sf 計算。

### §4.6 RegistryIndex façade

`entries[]` 仍是 backward-compatible 的 registry document 來源，但所有熱路徑查詢都應透過 `RegistryIndex` façade，避免 generator、police、catalog、adapter 各自掃陣列。

| Index | Key | Value | 主要使用者 |
|---|---|---|---|
| `atomIdIndex` | `ATM-CORE-0001` | atom entry ref | generator / registry diff / behavior engine |
| `mapIdIndex` | `ATM-MAP-0001` | map entry ref | map integration police / behavior.compose |
| `logicalNameIndex` | `atom.h2u.normalize-css-color` | node refs | human-readable query / catalog |
| `fingerprintIndex` | sf prefix 16 chars | node refs | dedup police |
| `versionIndex` | canonical ID | version list + current | cross-system compare / upgrade proposal |

`RegistryIndex` 可由既有 `registryDocument.entries` lazy build；初期不要求改 registry 儲存格式，但所有新增 lookup API 必須先走 index façade。這是 `ATM-2-0047` 的核心交付。

## §5 去重情境分類表（Dedup Police 工作清單）

地圖內原子和外面原子重複「**是合理的，不需要去重，除非外面那個單原子沒人在使用**」——這個直覺被機械化為以下 8 種情境：

| # | 情境 | 偵測訊號 | Police 行為 | 建議路徑 |
|---|---|---|---|---|
| 1 | 兩個自由原子 sf 100% 相同 | 同 sf、同 inputs、同 outputs | **強提示去重** | dedup proposal → human review |
| 2 | 兩個自由原子 sf 高相似（≥90%） | sf 不同但 LLM skill 評估相似 | **弱提示去重** | similarity report → 人類決定 |
| 2a | 兩個原子 sf 高相似且差異可多形化 | sf 差異可被維度參數解釋（ATM-POLY-001） | **建議 polymorphize** | polymorphize proposal（不是 merge） |
| 3 | Map 成員與另一自由原子相同 | 兩處 atomId 相同或 sf 相同 | **不去重**（合法重用） | only flag if 自由原子 zero callers |
| 4 | 同一 Map 內兩成員 sf 相同 | 同 sf 出現在 same mapId | **強提示合併** | dedup-within-map proposal |
| 5 | 不同 Map 各有功能等價成員 | sf 相同跨 mapId | **建議抽出共用** | extract-shared-atom proposal |
| 6 | Map 整體 sf 相同 | 兩 mapId 的 mapSemanticFingerprint 相同 | **強提示 map-level dedup** | map-merge proposal |
| 7 | Atom 完全沒有 caller | dependency-graph 顯示零入邊 | **建議 sweep** | mark deprecated → eventual removal |
| 8 | TTL 已到 | spec.ttl.expiresAt < now | **自動 expire** | mark expired + 通知 callers |

「Caller」定義：registry 中其他 atom/map 的 dependencies 引用，或 host adapter 報告的 runtime invocation。

## §6 行為分類學總表（10 個內建行為）

> 完整行為定義與警察使用關係詳見 [原子行為參考手冊](原子行為參考手冊.md)。

### §6.1 設計原則

1. **行為本身就是原子**：每個 behavior 是一顆 governed atom，可被 registry 管理、可被 hash-lock 鎖、可被另一個 behavior 觸發
2. **行為由 plugin 提供**：core 只定義 `AtomBehavior` interface 與 evidence schema；具體行為由 reference plugin pack 實作
3. **每個行為都有相同 5 個合約面**：trigger → evidence → gates → registry transition → rollback
4. **行為可組合**：dedup-merge = similarity-scan + merge + sweep；polymorphic-evolve = polymorphize + evolve

### §6.2 10 個內建行為

| # | 中文 | 英文行為 ID | 拓撲變化 | 主要 evidence | Lineage tag |
|---|---|---|---|---|---|
| 1 | 分裂 | `behavior.split` | 1 → 2+ | split-plan + 兩邊 sf | `bornBy: split` |
| 2 | 合併 | `behavior.merge` | 2+ → 1 | merge-plan + 合併後 sf | `bornBy: merge` |
| 3 | 串接（含樹狀） | `behavior.compose` | n atoms → 1 map | map composition + members[] | `bornBy: compose`（在 map） |
| 4 | 自動吞噬（去重） | `behavior.dedup-merge` | 2 → 1 | similarity-report + dedup-decision | `bornBy: merge`（dedup 變體） |
| 5 | 清理 | `behavior.sweep` | 1 → 1 (deprecated) | unused-report + caller list | 不改 lineage，只改 status |
| 6 | 演化 | `behavior.evolve` | 1@v1 → 1@v2 | upgrade-proposal + quality-comparison | `bornBy: evolve` |
| 7 | 自我毀滅（TTL） | `behavior.expire` | 1 → 1 (expired) | expiry-report | 不改 lineage |
| 8 | 多形 | `behavior.polymorphize` | 1 spec → n parametric instances | polymorph-template + param-spec | `bornBy: polymorphize` |
| **9** | **感染** | **`behavior.infect`** | **0 atoms → 1 patch plan** | **infect-plan + dry-run patch + 新 caller refs** | **legacy 端記錄注入點；atom 端 caller +1** |
| **10** | **轉化（原子化）** | **`behavior.atomize`** | **legacy 段 → 1 新 atom** | **atomize-proposal + 新 atom spec + 對映 legacy patch + sf** | **`bornBy: atomize`，parentRefs 指向 legacy source path** |

### §6.3 Legacy strangler 的兩個關鍵行為

第 9、10 項是 Legacy strangler 的核心動作，會直接由 ATM-3 / ATM-4 case study 實例化使用：

- **infect**：「我已經有 `atom.h2u.normalize-css-color`，請把 legacy `draft-builder.js` 中所有等價邏輯換成呼叫這個原子」——典型重用，**不創新原子**
- **atomize**：「我發現 legacy 中這段 `parseCssColor()` 邏輯沒有對應原子，把它抽成新原子並註冊」——典型抽出，**創新原子**

兩者通常成對使用：先 atomize 把 legacy 抽成原子，再 infect 把 legacy 中的其他重複呼叫點導向同一個原子。

**Lineage 對應**：

```jsonc
// atom 端
"lineage": {
  "bornBy": "atomize",
  "parentRefs": ["legacy://<host>/<path>#L1234-L1280"],
  "bornAt": "2026-06-01T00:00:00Z"
}
```

`legacy://` URI 在 host adapter 解析；upstream core 不知道這是哪個 host 的 path，只把它當不透明字串。

### §6.4 行為分類

| 分類 | 行為 |
|---|---|
| **Topology**（改拓撲） | split / merge / compose / dedup-merge / atomize |
| **Quality**（改能力不改身份） | evolve / polymorphize |
| **Sanitation**（移除或棄用） | sweep / expire |
| **Integration**（接入 legacy） | infect / atomize |

### §6.5 觸發條件補充

**behavior.split 三種觸發來源**：

| 觸發來源 | 偵測機制 | 說明 |
|---|---|---|
| 手動 | 人類提案 | 人類判斷原子職責過多 |
| Size police | 程式碼行數 / 複雜度超標 | 單檔過大或 cyclomatic complexity 超 threshold |
| **Demand police** ⭐ | usage tracking 偵測子功能被 ≥2 外部 caller 引用 | 需求驅動分裂：子功能已成共用基礎，應獨立成原子 |

**behavior.polymorphize 廣義多形觸發**：

不限於「只差參數」。任何高度相似 spec（差異可被維度參數解釋），皆為多形化候選：

| 維度 | 範例 | 多形方式 |
|---|---|---|
| 參數 | `parseCssColor(format: 'hex')` vs `(format: 'rgb')` | template + `params.format` |
| 輸入類型 | `normalize(input: string)` vs `(input: Buffer)` | template + `typeParam.input` |
| 輸出形狀 | `parse → {value}` vs `→ {value, metadata}` | template + `outputProfile` |
| 語言 | 同 spec 的 TypeScript vs Rust 實作 | template + `lang` |
| 品質 budget | 同功能但 timeout 不同 | template + `performanceProfile` |
| 行為變體 | `sort(stable: true)` vs `(stable: false)` | template + `variant` |

### §6.6 廣義多形化原則（ATM-POLY-001）

> **若兩個原子的 semantic fingerprint 差異可以被一個或多個「維度參數」解釋（即：用同一個 template + 不同參數值可以產出兩者的 spec），則它們必須被視為同一顆多形原子的不同實例。**

Dedup 比對遇到高相似原子時，必須先判斷「是否可 polymorphize」再決定是否 merge：
- 可多形化 → 建議 `behavior.polymorphize`（兩者都保留但歸為同一 template）
- 不可多形化 → 弱去重 report（建議 merge 或保留）

## §7 原子狀態機（無模糊地帶）

> 狀態機視覺圖：[atom-lifecycle-state-machine.svg](atom-lifecycle-state-machine.svg)

### §7.1 問題

現行 `registry.schema.json` 的 `status` enum `seed | active | experimental | deprecated | governed` 有重疊與含糊：

- `governed` 是「治理屬性」還是「狀態」？
- `seed` vs `governed` 都是 ATM-CORE 系列在用，分界不清
- 沒有「正在被某個 behavior 改造中」的狀態
- 沒有 TTL `expired` 終態
- 沒有 `quarantined`（被警察標記但尚未處置）

### §7.2 設計原則

1. **狀態與屬性分離**：`status` 是執行期狀態；`governance` 是治理層級屬性
2. **每個原子在任何時刻必須恰好處於一個 `status`**，不能多態
3. **狀態轉換必須由特定 behavior 觸發**，不能任意改

### §7.3 新狀態機

```
                 ┌──────────┐
                 │  draft   │  (新提案，尚未 validate)
                 └────┬─────┘
                      │ propose pass
                      ↓
                 ┌──────────┐
        ┌────────│ validated│  (validate pass，等待 promote)
        │        └────┬─────┘
        │             │ promote
        │             ↓
        │        ┌──────────┐
        │   ┌────│  active  │  ← 主執行期狀態
        │   │    └────┬─────┘

        │   │         │ behavior.<X> 啟動
        │   │         ↓
        │   │    ┌──────────────┐
        │   │    │transitioning │  (正在被 behavior 改造，鎖住寫入)
        │   │    └────┬─────────┘
        │   │         │ behavior 完成
        │   │         ↓
```

|---|---|---|---|---|
| `draft` | ✅ 限作者 | ❌ | ✅ propose only | ❌ |
| `validated` | ✅ | ❌ | ✅ promote / sweep | ❌ |
| `active` | ✅ | ✅ | ✅ 任何 behavior | ❌ |
| `transitioning` | ✅ 唯讀 | ❌ | ❌（鎖定） | ❌ |
| `deprecated` | ✅ | ⚠️ 警告 | sweep / atomize-replace | ❌ |
| `expired` | ✅ 唯讀 | ❌ | ❌ | ✅ |
| `quarantined` | ✅ 唯讀 | ❌ | clear / sweep | ❌ |

### §7.4a 部署範圍與可變性策略

除了 `status`（執行期狀態）和 `governance.tier`（治理層級），原子還有兩個獨立屬性控制部署行為與可變性：

**deployScope**（部署範圍）：

| 值 | 意義 | 編譯行為 |
|---|---|---|
| `all-env` | 所有環境可用（預設） | 正常編譯 |
| `dev-only` | 只在開發環境可用 | production build 排除 |
| `staging-only` | 只在 staging 可用 | production build 排除 |
| `test-only` | 只在測試中可用 | 不打包進任何 runtime build |

**mutabilityPolicy**（可變性策略）：

| 值 | 意義 | 行為限制 |
|---|---|---|
| `mutable` | 正常可改（預設） | 所有 behavior 皆可觸發 |
| `frozen-after-release` | 發布後凍結 | 一旦 `active` 且 `atomVersion ≥ 1.0.0`，只允許 `behavior.evolve`（產新版） |
| `immutable` | 永久不可改 | 任何 behavior 皆被拒絕；只有 sweep/expire 可退役 |

**governanceTier 的預設對應**：

| governanceTier | 預設 mutabilityPolicy | 預設 deployScope |
|---|---|---|
| `constitutional` | `immutable` | `all-env` |
| `governed` | `frozen-after-release` | `all-env` |
| `standard` | `mutable` | `all-env` |
| `experimental` | `mutable` | `dev-only` |

這些是預設值；任何原子都可以明確 override。`deployScope` 和 `mutabilityPolicy` 放在 **spec 檔**中（非 hot registry），因為它們是靜態屬性。

### §7.5 舊值 migration map

| 舊 status | 新 status | governance attr |
|---|---|---|
| `seed` | `active` | `tier: constitutional` |
| `active` | `active` | `tier: standard` |
| `experimental` | `validated` | `tier: standard` |
| `deprecated` | `deprecated` | （不變） |
| `governed` | `active` | `tier: governed` ⭐ 變屬性 |

新增獨立欄位 `governance.tier`：`constitutional | governed | standard | experimental`。

### §7.6 狀態-行為合法轉換矩陣

| 行為 | 起點要求 | 終點 |
|---|---|---|
| `behavior.split` | active | 兩個 active（lineage 留下） |
| `behavior.merge` | 都是 active | 1 個 active + N 個 deprecated |
| `behavior.dedup-merge` | active + active | 1 個 active + 1 個 deprecated |
| `behavior.evolve` | active@vN | active@vN+1（舊版仍 active 直到 sweep） |
| `behavior.sweep` | active 且 0 callers | deprecated |
| `behavior.expire` | deprecated 且 TTL 已到 / sweep 已過寬限 | expired |
| `behavior.polymorphize` | active | active (template) + N validated（實例 lazy） |
| `behavior.compose` | n 個 active | 同 atoms 不變，新增 1 個 map active |
| `behavior.infect` | 目標 atom 是 active | 目標 atom 不變，legacy 注入點記錄到 caller list |
| `behavior.atomize` | legacy 區段識別 + sf 計算 | 1 個 draft → validated → active（依 review） |

**mutabilityPolicy 限制**（優先於上表）：

| mutabilityPolicy | 允許的 behavior |
|---|---|
| `mutable` | 所有（依上表） |
| `frozen-after-release` | 僅 `behavior.evolve`（產新版），其餘 in-place 修改拒絕 |
| `immutable` | 僅 `sweep` / `expire`（退役），其餘全部拒絕 |

**Police 角色**：

- 任何違反此矩陣的 transition 嘗試 = hard fail
- `quarantined` 只能由警察寫入
- TTL 過期但仍在 active 狀態 = police flag
- `deployScope=dev-only` 出現在 production build = lifecycle police hard fail

### §8.1 擴充性保證

## §11 治理工具原子化路線圖

> 框架原則：「每個框架功能也要原子化（dogfooding）」。治理工具不是「只供原子使用的基礎設施」——它們本身也應該是 governed atoms。

### §11.1 三層保護模型下的原子化邊界

| 層 | 能否原子化 | 原因 | 範例 |
|---|---|---|---|
| **Layer 1 Constitutional** | ❌ 只能 hash-lock | 定義「什麼是原子」的 schema 不能自己是原子（自驗證悖論） | `atomic-spec.schema.json`、`registry.schema.json` |
| **Layer 2 Governed** | ✅ 必須原子化 | Seed atom（ATM-CORE-0001/0002）已證明可行 | Police plugins、Registry manager、CLI commands、Adapter interfaces、**治理工具** |
| **Layer 3 Mutable** | ❌ 不值得 | 配置檔用 git 管就夠 | `.atm/profile`、adapter configs |

### §11.2 兩階段演進

**Phase 1（ATM-3 scope）：Adapter 化**

- 每個 3KLife 治理工具改為 thin adapter，delegate 到 upstream adapter interface
- CLI 入口 100% 保留（硬規則）
- Shadow mode + parity test 驗證行為等價
- **這是過渡步驟，不是終態**

**Phase 2（Alpha1+ scope）：原子化**

- 每個 adapter 實作升格為 governed atom（ATM-GOV-* 系列）
- ProjectAdapter 變成路由 façade，每個 GovernanceStore 背後是獨立原子
- 每顆原子可被：獨立 evolve、獨立 test、獨立替換、被其他 repo 選擇性重用、被警察治理（hash-lock + drift 偵測）

### §11.3 compute-gate 原子 map 化範例

compute-gate 天然適合 atom map 化——9 個 gate 就是 9 顆獨立原子：

| Atom ID | 功能 | 類型 |
|---|---|---|
| ATM-GOV-0005 | TypeScript 語法掃描 | gate |
| ATM-GOV-0006 | 檔案編碼完整性 | gate |
| ATM-GOV-0007 | UI Spec 三層契約驗證 | gate |
| ATM-GOV-0008 | 任務範圍守衛 | gate |
| ATM-GOV-0009 | 文件分片健康檢查 | gate |
| ATM-GOV-0010 | 模組邊界守衛 | gate |
| ATM-GOV-0011 | ESLint 關鍵規則掃描 | gate |
| ATM-GOV-0012 | 死碼偵測 | gate |

`--profile quick` vs `standard` 成為 map member 選擇器，而非硬編碼的 profile 分支。

### §11.4 與 ATM-3 任務卡的對應

所有 ATM-3-0006~0011 已追加「Phase 1 = adapter 化 / Phase 2 = 原子化」兩階段路徑。ATM-3-0001 的 capability matrix 須標註每個工具的原子化計畫。

但這仍只覆蓋到「單一治理工具」層級，還沒有一張 end-to-end 卡把整套 task card system 收斂成 atomic map。為了落實 dogfooding，新增 `ATM-3-0015` 補上這個缺口：task-card-opener、task-lock、task shard、task-scope、doc-id sync 不能只各自標註「Phase 2 會原子化」，必須再有一張卡定義它們如何組成同一條 governed task lifecycle。

### §11.5 Task Card System Atomic Map（新增規劃缺口）

`ATM-3-0015` 的目標不是再做一支 monolith helper，而是把現行 task card workflow 拆成可治理的 member atoms / compute nodes：

| 節點 | 責任 | 現行對應 |
|---|---|---|
| `allocateTaskId` | 推導下一個合法卡號，不得撞既有 task card / shard / lock | `task-card-opener.js` + `task-lock reserve` |
| `reserveTaskId` | 在多人併發下原子保留卡號 | `task-lock.js` |
| `openTaskCard` | 產出 Markdown task card 與 frontmatter | `task-card-opener.js` |
| `lockTaskScope` | 寫入 canonical `files[]` scope 與 lock metadata | `task-lock.js` |
| `writeTaskShard` | 更新 task aggregate/shard 真相 | `tasks-atm` / `shard-manager.js` |
| `validateTaskShard` | 驗證 part 必須為合法 JSON array、門檻與摘要規則成立 | 新增 publish validator |
| `syncDocRegistry` | 將新卡回寫 doc_id registry / 索引 | `doc-id-registry.js` |
| `finalizeTaskLifecycle` | open/in-progress/done 轉換與 unlock / evidence 封口 | `finalize-agent-turn.js` + `task-lock.js` |

原則上，`TaskAdapter` / `LockAdapter` / `ShardAdapter` / `RuleGuardAdapter` 只各自提供 seam；真正的 end-to-end 任務卡生命週期必須由一條 task card atomic map 統一編排，否則 ATM 仍然只是「有很多治理工具」，不是「自己的治理工具也被治理」。

### §11.6 Framework Function Atomization Coverage Gate（新增規劃缺口）

`ATM-3-0015` 補的是 task card system，但「每個框架功能也要原子化」的範圍更大。若沒有 framework-wide coverage manifest，ATM 仍可能只把幾個治理工具原子化，卻漏掉 CLI protocol、Registry、Spec / Scaffold、Test / Report、Evidence、Police、Adapter、Map、PEV / Lifecycle docs 等核心功能群。

因此新增 `ATM-2-0050`，建立 `framework-function-atomization-manifest.md` 與 deterministic validator。這張卡只補 coverage gate，不重複 AtomGenerator、MapGenerator、task card lifecycle 或既有 adapter 化任務。

| 功能群 | 例子 | coverage 要求 |
|---|---|---|
| CLI protocol | `atm init`、`atm create`、`atm verify`、`atm map` | 每個 command 必須能映射到 atom、atomic map 或 adapter facade |
| Spec / scaffold / generator | Atomic Spec loader、scaffold builder、AtomGenerator | 不得繞過 generator provenance；pre-generator 產物需 backfill witness |
| Registry / hash / index / catalog | registry manager、hash-lock、RegistryIndex、catalog export | 必須有 registry entry / map entry / validation evidence |
| Test / report / evidence | test runner、report schema、artifact log、usage-feedback | 必須能被 validation evidence 與 caller-count 回填追蹤 |
| Police / governance gates | neutrality scanner、rule guards、encoding/context/import guards | 每個 guard 必須是 governed atom 或 atomic map member，並輸出 `trigger / scope / severity / action` 的 machine-readable findings |
| Adapter interfaces | TaskAdapter、LockAdapter、ShardAdapter、RuleGuardAdapter | adapter 只能做 facade，背後能力要拆 ATM-GOV atoms |
| Task lifecycle / PEV / map | task card flow、PEV proposal、Atomic Map workflow | 由 `ATM-3-0015`、`ATM-2-0023`、`ATM-2-0050` 分工覆蓋，不互相誤認為完成 |

Police surfaces 預設是 active routed surfaces，不再只是驗收時的 pass/fail：`authoring-time`、`transition-time`、`sweep-time` 都要能產生 findings，低風險先進 `ATM-2-0035` advisory / human review queue，高風險再走 follow-up task card、quarantine 或 hard fail。

validator 規則：任一 Layer 2 framework function 若沒有 manifest entry，或沒有 atom / atomic map / adapter facade / open task 對應，必須 fail；Layer 1 只允許 `constitutional-exception`，Layer 3 只允許 `mutable-exception`。

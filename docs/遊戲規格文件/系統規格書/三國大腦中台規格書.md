## A. 系統描述

三國大腦中台是一套負責「把三國文本變成可查、可控、可生成遊戲內容」的資料與推論服務。它的第一優先任務不是先寫 Cocos UI，而是先完成《三國演義》PDF 到 Markdown、資料清洗、章回切片、人物事件抽取、persona card 生成、向量化入庫與 RAG 查詢閉環。

本中台提供四類能力：

1. **文本資料管線**：將《三國演義》PDF 轉成乾淨 Markdown，拆成章回與語意 chunk，抽取人物、事件、地點、人際關係與原文引用。
2. **知識檢索服務**：以 Pinecone 作為研發 / 雲端向量庫，依 `generalId + contextKey + metadata filter` 取回可信背景。
3. **角色生成服務**：結合 persona card、歷史片段、玩家日誌與模型推論，回傳符合武將性格的一句話、日誌反應或模板補丁。
4. **關鍵字互動服務**：由 ETL 管線自動整理與武將高度相關的互動關鍵字，供玩家在人物頁點擊後選詞發話，武將再以其歷史視角與 persona 口吻回應聯想內容。

Unity 對照：本中台相當於 `Narrative Backend + RAG Service + Dialogue Authoring Pipeline`。Cocos 端只呼叫 API 與接收 DTO，不直接承擔 PDF 清洗、向量索引與大型模型推論。

## C. 技術架構

### C-1. MVP 技術棧

| 層級 | 工具 | 用途 |
|---|---|---|
| PDF 轉換 | Docling；Marker 作備援 | PDF to Markdown，保留章回結構 |
| 清洗與切片 | Python + Pydantic + LangChain text splitters | 清理頁碼、章回切片、schema 驗證 |
| 抽取模型 | Gemini / Vertex AI / 本地 Qwen | 抽取人物、事件、關係與摘要 |
| 向量庫 | Pinecone | 雲端 / 研發向量檢索 |
| Embedding | bge-m3 / text2vec / OpenAI embeddings | 將 chunk 與事件轉向量 |
| API | FastAPI + Uvicorn | 提供 Cocos 呼叫入口 |
| Runtime LLM Provider | Gemini / Ollama / vLLM / llama.cpp；以 adapter 抽象 | 台詞生成與模板補丁，可依環境分流與 fallback |
| 本地降級 | SQLite-vec / 模板 JSON | 無網路或低階設備時使用 |

### C-2. 服務分層

```text
Cocos Creator
  -> NpcDialogueService
  -> FastAPI /v1/npc/dialogue
  -> Persona Card Store
  -> Evidence Resolver / Vector Retrieval
  -> LLM Provider Router
  -> Gemini / Ollama / vLLM / llama.cpp Inference
  -> Safety / Drift Guard
  -> DialogueResponse DTO
```

正式遊戲不得把 Pinecone 視為唯一真相。Pinecone 是知識與記憶的檢索層；武將 canonical roster、人物頁資料與存檔真相仍以本地 JSON / Data Schema / Server Save 為權威。

### C-3. Evidence Resolver

`evidenceRefs` 是證據座標，不是證據內容。它的角色類似 Unity 的 GUID / Addressable key：能定位資產，但不能取代被載入的 asset 本體。因此 LLM prompt 不得只傳 `evidenceRefs`；在呼叫任何 Gemini / Ollama / vLLM / llama.cpp adapter 前，中台必須先經過 `EvidenceResolver` 將 ref 展開成最小可讀證據包。

Evidence Resolver 的輸入：

- `generalId`
- `contextKey`
- `selectedKeywordKeys`
- `personaCard.evidenceRefs`
- `keyword.sourceRefs`
- `retrievalPolicy`

Evidence Resolver 的輸出必須是 `ResolvedEvidencePack`：

```json
{
  "contextKey": "changban-bridge",
  "resolvedEvidence": [
    {
      "evidenceRef": "042#p2",
      "sourceType": "romance",
      "chapterNo": 42,
      "sourceQuote": "<由 EvidenceResolver 從 042#p2 載入的原文摘句>",
      "factSummary": "張飛在長坂橋斷後，以喝聲震懾追兵，替劉備爭取退走時間。",
      "generalIds": ["zhang-fei", "liu-bei", "cao-cao"],
      "confidence": 0.9
    }
  ],
  "unresolvedEvidenceRefs": []
}
```

規則：

1. `evidenceRef` 只可作為 trace / citation，不可單獨作為 LLM 理解事件的依據。
2. `sourceQuote` 可是原文摘句或清洗後短句；若原文太長，必須同時提供 `factSummary`，並限制 prompt 只帶 3~5 條高信心片段。
3. `factSummary` 是 deterministic summarizer 或人工審核資料的摘要，不可由 runtime LLM 臨場補造。
4. 若 `unresolvedEvidenceRefs` 非空且沒有足夠 `resolvedEvidence`，進入 fallback，不呼叫生成模型硬編劇情。
5. 向量庫只負責召回候選；Evidence Resolver 必須再用 metadata filter、confidence、reviewStatus 與 persona / keyword 交集做二次篩選。

### C-4. LLM Provider Router 與多層 Fallback

中台的生成層必須以 adapter / provider 介面抽象，不得在 `NpcDialogueService` 直接硬綁 Gemini、Ollama 或單一模型字串。建議介面：

```text
DialogueProvider.generate(DialoguePromptPackage) -> DialogueGenerationResult
```

`DialoguePromptPackage` 至少包含：

- `personaCardSubset`
- `selectedContext`
- `selectedKeywords`
- `resolvedEvidence`
- `playerContext`
- `outputContract`
- `providerPolicy`

Provider 分層：

| Priority | Provider | 用途 | Fallback 條件 |
|---|---|---|---|
| P0 | `DeterministicTemplateProvider` | 無模型、安全保底、測試 baseline | 永遠可用 |
| P1 | `GeminiProvider` | 雲端高品質 reasoning / prompt QA | API timeout、quota、JSON invalid、policy fail |
| P2 | `LocalLlamaProvider` | 地端 Llama-3 / Qwen / Ollama | 本地服務未啟動、VRAM 不足、超時 |
| P3 | `VllmProvider` | 第二階段本地高吞吐服務 | GPU queue 滿、模型不可用 |
| P4 | `MockProvider` | CI / smoke test | 僅測試環境 |

Router 行為：

1. 依 `NPC_LLM_PROVIDER_ORDER=gemini,local_llama,vllm,deterministic` 決定嘗試順序。
2. 每個 provider 必須回傳統一 schema，不得讓 Cocos 端知道模型差異。
3. 任一 provider 失敗後，Router 記錄 `providerTrace`，再嘗試下一層。
4. 所有 provider 都失敗時，回 `personaCard.safeFallbackLine`，`fallbackUsed=true`。
5. LLM 輸出不得寫回 canonical persona card、canonical event 或 relationship edge；只能作為 runtime dialogue result 或待審候選。

建議環境變數：

```text
NPC_LLM_PROVIDER_ORDER=gemini,local_llama,vllm,deterministic
NPC_LLM_MODEL_GEMINI=gemini-2.5-pro
NPC_LLM_MODEL_LOCAL=llama3.1:8b-instruct-q4_K_M
NPC_LLM_TIMEOUT_MS=2500
NPC_LLM_MAX_RETRIES=1
NPC_VECTOR_PROVIDER_ORDER=pinecone,chroma,sqlite_vec
```

Unity 對照：`LLM Provider Router` 類似一個 ScriptableObject strategy list。遊戲邏輯只依賴共同介面，實際要走雲端 Gemini、地端 Llama 或 deterministic template，可以由設定檔切換。

### C-6. 互動記憶規劃接入範圍

`NPC Brain Memory System` 是本中台的玩家-武將互動記憶子規格。它與 `local/npc-dialogue-history.jsonl` 的定位不同：history cache 只回收成功台詞，互動記憶則以 `(saveId, generalId)` 保存玩家與單一武將之間的壓縮關係狀態，供後續 dialogue prompt 注入。

第一輪只納入 M1-M4，目標是讓 server 具備可驗證的資料合約與 prompt 注入能力：

| Milestone | 範圍 | 交付物 |
|---|---|---|
| M1 Schema & Models | 定義 `InteractionEvent`、`GeneralMemoryData`、`GeneralMemoryContext` 與 Cocos TypeScript interface | `server/npc-brain/app/interaction_memory.py`、`NpcDialogueService.ts` 型別擴充 |
| M2 Storage I/O | 以 JSONL append 保存原始事件，以 JSON atomic write 保存壓縮記憶 | `local/interaction-events/<saveId>__<generalId>.jsonl`、`local/general-memory/<saveId>__<generalId>.json` |
| M3 Memory API | 新增互動事件寫入、記憶讀寫與同步壓縮入口 | `/v1/npc/interaction-events`、`/v1/npc/general-memory`、`/v1/npc/memory/compress` |
| M4 Dialogue Injection | `POST /v1/npc/dialogue` 支援 `saveId` 與 `memoryContext`，在 prompt 中注入 `playerGeneralMemory` | `DialogueRequest.saveId`、`DialoguePromptPackage.memoryContext`、provider prompt 注入 |

M5 四段 LLM 壓縮與 M6 Cocos adapter 屬第二輪。M5 必須遵守 `lastCompressedIdx` 安全指針，只能在四段壓縮全部成功且 atomic write 完成後推進；M6 才把 Cocos 完成對話後的事件回寫接入正式事件系統。

Unity 對照：這相當於把「每個存檔中某位 NPC 對玩家的關係摘要」做成一份小型 SaveData + Runtime Context Provider。Persona card 像 ScriptableObject 原型，互動記憶像每個 save slot 的 instance state，兩者不得互相覆寫。

## E. 資料處理流程

### E-1. Phase 0：來源確認

1. 確認《三國演義》PDF 來源可用於研發資料處理。
2. 建立 `source-manifest.json`，記錄書名、版次、來源、授權狀態、轉換工具與 hash。
3. 若有可靠公版純文字，可作為交叉驗證；但本練習流程以 PDF -> Markdown 為主。

### E-2. Phase 1：PDF 轉 Markdown

1. 使用 Docling 轉換 PDF，Marker 作備援。
2. 輸出 `source.md`。
3. 保留章回標題，不保留頁碼、頁首、頁尾與掃描雜訊。
4. 產出 `conversion-report.json`，列出頁數、章回數、可疑 OCR 區段。

### E-3. Phase 2：Markdown 清洗與章回拆分

1. 依「第 X 回」或章回標題切成 `chapters/ch_###.md`。
2. 移除空白重複、頁碼、廣告、註解殘片。
3. 保留 paragraph index 與 source offset，供未來 evidence reference 使用。
4. 產出 `chapters-manifest.json`。

### E-4. Phase 3：武將主名冊、文本稱呼表與正式對照表

1. Phase 3 的資料模型拆三層：
  - `武將主名冊`：來自 `assets/resources/data/generals.json`，只負責定義 canonical `generalId`、主名、陣營與目前已採納的稱呼。它是產品內部的 identity seed，不宣稱自己就是文本原始來源。
  - `文本稱呼表`：記錄文本裡實際觀察到的稱呼字串、`sourceRef`、章回、段落、場景參與者等。這一層才是一手 evidence。
  - `正式對照表`：只收錄經規則或人工審核後，可以安全映射到 `generalId` 的稱呼對照，供後續召回與消歧使用。
2. 目前 `server/npc-brain/pipelines/sanguo-rag/build_alias_dict.py` 先產出 `武將主名冊` 與 `正式對照表` 的 bootstrap 版本；`server/npc-brain/pipelines/sanguo-rag/collect_observed_mentions.py` 再蒐集 `文本稱呼表`，兩者不得混成同一步。
3. 初始正式對照來源分四層：
  - `武將主名冊` 既有欄位：`name`、`alias[]`、`title`
  - `title` 去除 `【】` 等裝飾後可直接採納的稱號詞
  - tracked manual overrides：人工補強字號、稱號與演義稱呼，例如張飛、張翼德、翼德、燕人張翼德
  - 後續拆文流程中觀察到的 `文本稱呼候選`，但不得在同一輪自動升格為正式對照
4. `將軍`、`主公`、`先生`、`縣令`、`太守` 等泛稱預設不是高信心正式對照；它們屬於情境稱呼，必須在後續對話解析階段依場景消歧。
5. `文本稱呼候選` 只能先進 review queue，不得直接覆寫正式對照表；每次版本升級最多做一輪「候選蒐集 -> 人工審核 -> 發佈 vNext」，避免稱呼對照自我擴張成無限循環。
6. 抽取結果不得直接創建 runtime 武將；必須先映射回 canonical `generalId`。

### E-5a. Phase 4a：對話解析與稱呼消歧

每個 chunk 在事件抽取前，先做 deterministic-first 的對話解析與稱呼消歧。

1. 先切分旁白與引號內容，辨識 `speaker`、`addressee`、`mentioned target`。
2. 先用正式對照表做候選召回，再結合前後文中的場景參與者、說話動詞、稱呼位置與文本稱呼表中的已觀察稱呼，解析 `將軍`、`主公`、`先生` 等泛稱的實際指向。
3. 若引號中未直接出現人名，但旁白已指明對話雙方，仍應把泛稱解析為對應 `generalId`；若證據不足，保留 `unresolved address title`，不得硬綁人物。
4. 對話解析階段可同時抽出 `item`、`location`、`creature` 等 mention，但這些 mention 與人物的關係，必須在事件抽取階段正式定義。

```json
{
  "sourceRef": "ch_042#p18",
  "sceneParticipants": ["zhang-fei", "liu-bei"],
  "utterances": [
    {
      "speakerLabel": "軍士",
      "speakerGeneralId": null,
      "addresseeLabel": "將軍",
      "addresseeGeneralId": "zhang-fei",
      "resolutionMode": "scene-address-title",
      "text": "將軍，我送您一把寶刀！"
    }
  ],
  "entityMentions": [
    {
      "label": "將軍",
      "entityType": "address-title",
      "resolvedGeneralId": "zhang-fei",
      "confidence": 0.86
    },
    {
      "label": "寶刀",
      "entityType": "item",
      "resolvedItemKey": null,
      "confidence": 0.73
    }
  ]
}
```

### E-5b. Phase 4b：事件抽取

每個 chunk 在完成正式對照召回與對話解析後，再用 LLM 或結構規則做事件抽取。

1. 事件抽取的輸入至少包含：原始 chunk、正式對照候選、scene participants、utterance resolution、entity mentions。
2. 若對話中出現泛稱與物品互動，例如「將軍，我送您一把寶刀」，事件抽取必須把 `寶刀 -> offered_to -> zhang-fei` 這類關係明確寫成 edge，而不是只記錄字面共現。
3. 若泛稱未能在 E-5a 消歧成功，事件抽取只能保留 unresolved participant，不得為了完整事件而強行綁定錯誤 `generalId`。

```json
{
  "eventId": "romance.ch042.zhang-fei.changban-bridge",
  "chapterNo": 42,
  "eventKey": "changban-bridge",
  "generalIds": ["zhang-fei", "liu-bei", "cao-cao"],
  "location": "長坂橋",
  "summary": "張飛據橋斷後，以大喝震懾曹軍。",
  "sourceQuote": "燕人張翼德在此...",
  "relationshipEdges": [
    {
      "from": "zhang-fei",
      "to": "liu-bei",
      "type": "protects",
      "edgeConfidence": 0.86,
      "edgeStrength": 0.92
    }
  ],
  "moodTags": ["bold", "loyal", "intimidating"],
  "confidence": 0.92,
  "sourceRef": "ch_042#p18"
}
```

補充：`relationshipEdges[].edgeConfidence` 代表抽取器對這條 edge 是否成立的信心；`edgeStrength` 才是可選的語意強度。兩者不得再共用單一 `confidence` 欄位。

補充：`changban-bridge` 這類 hand-authored `gold seed spec` 只應保留少量 `gold seed / regression fixture`；正式量產事件必須以通用抽取器 + schema gate + review queue 為主，不能要求每個歷史事件都手寫一個 builder。現行做法已先收斂成「`gold_seed_registry.py` + `extract_battle_cluster()` + `build_gold_seed_battle_event()`」三段式。另有 `generic-battle-candidate-v1` 會輸出 review-only 候選到 `generic-battle-candidates.jsonl`，未審核前不得進 keyword / persona / API。

### E-6. Phase 5：互動關鍵字抽取與分類

ETL 必須和事件抽取一起產出可供遊戲互動的關鍵字集合，供玩家點擊張飛等武將時挑選。

1. 關鍵字來源以 `generalId` 關聯的事件、關係、章回片段、persona card 錨點為主，不可只靠單一 chunk 臆測。
2. 每個關鍵字必須至少包含：`keywordKey`、`label`、`category`、`generalIds`、`sourceRefs`、`confidence`。
  - `label` 是 UI 顯示用短標籤，必須可放進 Cocos 下拉選單；MVP 建議上限：人物 / 地點 / 物品 / 生物 8 字，事件 10 字。
  - 若事件摘要較長，完整語意需放入 `fullLabel` 或事件本體的 `summary`，不得直接把長句塞進 `label`。
  - 例如事件 `changban-bridge` 的 UI label 應為「長坂橋斷後」，完整描述「張飛據長坂橋斷後，以大喝震懾曹軍，為劉備爭取退走時間。」保留在 `fullLabel` / `summary`。
3. MVP 先支援以下分類：
   - `person`：明確人物名、職稱人物、集團人物稱呼，例如張飛、劉備、某縣令、黃巾賊。
   - `event`：重要事件、戰役、盟約、斷後、護送、出征等可成為對話焦點的事件名稱或事件鍵。
   - `location`：城池、橋、關口、郡縣、山川、營寨等與武將經歷明確相關的地點。
   - `item`：武器、裝備、旗幟、車船、器械、文書、酒肉等無生命可見物件。
   - `creature`：馬、牛、犬、鷹等有生命生物，不含泛用抽象比喻。
4. 未來可擴充更多分類，但 category key 必須保持可機器判斷，不得把 UI label 直接當 enum。
5. 去噪原則：只保留可支撐武將聯想或歷史敘事的詞；純背景風景、無敘事功能的路人甲乙、一次性掃描噪音詞不得進正式 keyword pack。
6. 關鍵字不得直接創建 runtime 實體；人物類仍必須先映射回 canonical `generalId` 或標記為 `non-roster person`。
7. 輸出位置建議放在 `artifacts/data-pipeline/sanguo-rag/extracted/keyword-options/`，每位武將可生成一份 `generalId.keywords.json`。

```json
{
  "generalId": "zhang-fei",
  "keywordVersion": "general_keywords_v1",
  "categories": {
    "person": [
      {
        "keywordKey": "liu-bei",
        "label": "劉備",
        "generalIds": ["zhang-fei", "liu-bei"],
        "sourceRefs": ["ch_042#p18"],
        "confidence": 0.96
      }
    ],
    "event": [
      {
        "keywordKey": "changban-bridge",
        "label": "長坂橋斷後",
        "fullLabel": "張飛據長坂橋斷後，以大喝震懾曹軍，為劉備爭取退走時間。",
        "uiLabelMaxChars": 10,
        "generalIds": ["zhang-fei"],
        "sourceRefs": ["romance.ch042.zhang-fei.changban-bridge"],
        "confidence": 0.94
      }
    ],
    "location": [
      {
        "keywordKey": "changban-bridge-location",
        "label": "長坂橋",
        "generalIds": ["zhang-fei"],
        "sourceRefs": ["ch_042#p18"],
        "confidence": 0.93
      }
    ]
  }
}
```

### E-7. Phase 6：去重、歸納與 Persona Card

1. 合併跨 chunk 的同一事件。
2. 為每位武將生成 persona card，且此步必須在連接 Gemini / Ollama / vLLM 等 LLM backend 前完成。Persona card 是 LLM 的角色邊界，不是 LLM 自行發明的人格。
3. persona card 至少包含：`generalId`、`displayName`、`personaVersion`、`voiceStyle`、`personalityTraits`、`relationshipAnchors`、`keywordAnchors`、`moodAnchors`、`evidenceRefs`、`safeFallbackLine`、`taboos`、`llmPromptRules`、`manualReviewRequired`。
4. `voiceStyle` / `personalityTraits` 可由武將名冊、事件 moodTags、relationship edges 與人工 preset 合成；但所有可回扣史實的內容仍須有 `evidenceRefs`。
5. 張飛、關羽、趙雲、曹操、劉備、諸葛亮等核心名將的 persona card 必須標記 `manualReviewRequired=true`，LLM pilot 前先人工抽查。
6. `safeFallbackLine` 是中台失敗、LLM timeout、JSON parse fail 或 evidence 不足時的安全台詞來源；不得等到 LLM 接好後才補。
7. 低信心資料進 `review/low-confidence-events.jsonl`，不入正式向量庫。

### E-8. Phase 7：Embedding 與 Pinecone 入庫

1. `romance_facts_v1`：演義事件與原文片段。
2. `history_facts_v1`：正史或百科摘要，若資料源不同需獨立 namespace。
3. `general_persona_v2`：persona card 與核心錨點；relationship anchors 使用 `edgeConfidence` / `edgeStrength`。
4. `general_keywords_v1`：互動關鍵字與分類錨點；僅收正式 keyword pack，不收低信心髒詞。
5. `player_memory_dev`：玩家互動摘要，MVP 可先只 dev namespace。

Metadata 必含：`generalIds`、`eventKey`、`chapterNo`、`sourceType`、`faction`、`confidence`、`sourceRef`。

補充：Embedding / vector DB 的輸出不能直接送給 LLM。所有召回結果必須先進 Evidence Resolver，整理成 `ResolvedEvidencePack` 後再組 prompt。向量分數只代表語意相似，不代表 canonical 正確性。

Response 範例：

```json
{
  "ok": true,

    "defaultProvider": "pinecone",
    "providerOrder": ["pinecone", "qdrant", "sqlite_vec"]
  }

```

### F-2. `GET /v1/npc/context-options`

Query：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `generalId` | string | 武將 canonical id |
| `limit` | number | 回傳情境數量 |

Response：

```json
{
  "generalId": "zhang-fei",
  "options": [
    { "contextKey": "changban-bridge", "label": "長坂橋", "sourceType": "romance", "confidence": 0.92 },
    { "contextKey": "taoyuan-oath", "label": "桃園結義", "sourceType": "romance", "confidence": 0.89 }
```


### F-4. `POST /v1/npc/dialogue`

Request：

```json
{
  "generalId": "zhang-fei",
  "contextKey": "changban-bridge",
  "selectedKeywordKeys": ["liu-bei", "serpent-spear"],
  "toneMode": "in-character",
  "locale": "zh-TW",
  "speechContextMode": "life_chat",
  "llmModelPreset": "fallback_chain",
  "maxChars": 60
}
```

目前實作欄位以 `generalId`、`contextKey`、`selectedKeywordKeys`、`toneMode`、`locale`、`speechContextMode`、`llmModelPreset`、`maxChars` 為基準。`playerId` / `playerContext` 屬互動記憶與玩家上下文下一階段欄位，需等 memory API 與 `saveId` 注入完成後再升格為正式 runtime 契約。

Response：

```json
{
  "generalId": "zhang-fei",
  "contextKey": "changban-bridge",
  "locale": "zh-TW",
  "speechContextMode": "life_chat",
  "llmModelPreset": "fallback_chain",
  "text": "長坂橋頭那聲喝，俺不是為逞勇，是要替大哥斷開曹軍的膽。",
  "evidenceRefs": ["romance.ch042.zhang-fei.changban-bridge"],
  "usedEvidenceRefs": ["romance.ch042.zhang-fei.changban-bridge"],
  "usedKeywords": [
    { "keywordKey": "liu-bei", "category": "person", "label": "劉備", "sourceRefs": ["ch_042#p18"] }
  ],
  "rejectedKeywordKeys": [],
  "fallbackUsed": false,
  "generationMode": "local-llama-json-v2+persona-card+quality-guard",
  "provider": "local_llama",
  "model": "llama3.1:8b-instruct-q4_K_M",
  "providerTrace": ["gemini:timeout", "local_llama:ok"],
  "qualityWarnings": [],
  "repairUsed": false
}
```

目前 runtime / Cocos 端主欄位是 `text`。若未來需要相容舊文件或外部 client 的 `line` 欄位，應新增 alias task；不得讓 `text` 與 `line` 分別代表不同內容。

規則：

1. `contextKey` 與 `selectedKeywordKeys` 可同時存在；若兩者衝突，以 `generalId + selectedKeywordKeys` 的交集 evidence 為優先。
2. 若玩家只選關鍵字、不選事件，中台仍可回應，但必須回扣該關鍵字的 `sourceRefs`。
3. 若玩家選到低信心或已淘汰 keyword，中台須回退到 persona card 的安全聯想，不得硬編重大史實。
4. `providerTrace`、`fallbackUsed`、`qualityWarnings`、`repairUsed` 是 QA 判斷真 LLM 成功、模型修補或 deterministic fallback 的必要欄位，不可在 Cocos debug UI 中隱藏。

### F-5. `POST /v1/npc/dialogue/stream`

第二階段支援。Web Preview 可用 SSE / chunked response；Native 端若 Cocos JSB 不穩定，回退短輪詢或非串流。

### F-6. 互動記憶 API（M1-M4 Planned）

互動記憶 API 由 `NPC Brain Memory System` 定義，第一輪只要求本機 JSONL / JSON storage 與 prompt 注入可驗證，不要求正式資料庫或向量化。

| Endpoint | 狀態 | 用途 |
|---|---|---|
| `POST /v1/npc/interaction-events` | Planned | Cocos 在玩家-武將互動完成後寫入事件，server 補 `eventId` / `createdAt`，append 到 JSONL |
| `GET /v1/npc/general-memory` | Planned | 依 `saveId + generalId` 讀取目前壓縮記憶；不存在時回空白 `GeneralMemoryData` |
| `POST /v1/npc/general-memory` | Planned | 開發與偵錯用，atomic write 指定武將記憶 |
| `POST /v1/npc/memory/compress` | Planned | 同步觸發壓縮；M3 可先 stub，M5 再接四段 LLM 壓縮 |

`POST /v1/npc/dialogue` 接入記憶後的規則：

1. 若 request 帶 `saveId` 且未帶 `memoryContext`，server 自動讀取 `local/general-memory/<saveId>__<generalId>.json`。
2. 若 request 已帶 `memoryContext`，視為開發 override，server 不再 auto-fetch。
3. 若 `shortTerm`、`longTerm`、`playerProfile`、`promises` 四段全空，prompt 必須完全省略 `playerGeneralMemory`，避免浪費 token。
4. `playerGeneralMemory` 必須放在 persona 之後、resolved evidence 之前；它描述玩家與此武將的 instance state，不得覆寫 canonical persona card 或 canonical event。

## G. Prompt 與生成規則

### G-1. Prompt 組合順序

1. System：三國世界觀、安全規則、不得自稱 AI。
2. Persona：武將 persona card、口吻、關係、禁忌。
3. Resolved Evidence：Evidence Resolver 展開出的 3~5 條高信心 `sourceQuote / factSummary`，不可只放 `evidenceRefs`。
4. Keyword Intent：玩家已選的 keyword labels、category、keyword-specific evidence refs。
5. Player Context：玩家當前選擇的下拉情境與補充文字。
6. Output Contract：只輸出一句 20~60 字繁體中文台詞與 emotion tag。

Prompt package 範例：

```json
{
  "personaCardSubset": {
    "generalId": "zhang-fei",
    "displayName": "張飛",
    "voiceStyle": ["豪烈", "直白", "護主重義", "短句有力"],
    "taboos": ["不可怯戰", "不可背棄劉備", "不得新增未提供 evidence 的重大史實"]
  },
  "selectedContext": { "contextKey": "changban-bridge", "label": "長坂橋" },
  "resolvedEvidence": [
    {
      "evidenceRef": "042#p2",
      "sourceQuote": "<由 EvidenceResolver 從 042#p2 載入的原文摘句>",
      "factSummary": "張飛在長坂橋斷後，震懾追兵，替劉備爭取退走時間。"
    }
  ],
  "selectedKeywords": [
    { "keywordKey": "cao-cao", "label": "曹操", "category": "person" }
  ],
  "outputContract": { "language": "zh-TW", "maxChars": 60, "format": "json" }
}
```

LLM 看到的是 `sourceQuote / factSummary`；`evidenceRef` 只用來讓輸出回扣證據來源。

### G-2. 禁止事項

1. 不得產生未檢索到的重大史實。
2. 不得讓武將知道玩家未記錄的隱私或跨存檔資訊。
3. 不得使用現代網路語、破第四面牆或自稱模型。
4. 不得把玩家輸入直接覆蓋進 persona card。

### G-3. Fallback

若 Pinecone 無命中、LLM timeout、內容審查失敗或 JSON parse 失敗，回傳 persona card 的 `safeFallbackLine`，並標記 `fallbackUsed=true`。

Fallback 層級：

1. 同 provider 重試一次，僅限 transient error。
2. 依 `NPC_LLM_PROVIDER_ORDER` 切下一個 provider。
3. 所有 LLM provider 失敗時，使用 deterministic template。
4. deterministic template 仍缺 evidence 時，使用 `safeFallbackLine`。

每次 fallback 都必須保留 `providerTrace`，供 QA 追查是 Gemini 失敗、地端 Llama 失敗、向量召回不足，還是 output contract validation 失敗。

若玩家有選 `selectedKeywordKeys`，fallback 句仍應優先保留對該關鍵字的弱聯想，但不得虛構不在 evidence 內的重大史實。

## H. Cocos 串接要求

1. Cocos 端新增 `NpcDialogueService` 包裝 API，不允許 UI component 直接散落 fetch。
2. UI 下拉選項由 `GET /v1/npc/context-options` 取得，不在前端硬寫事件清單。
3. 人物頁 `GeneralDetail` 應可額外呼叫 `GET /v1/npc/keyword-options`，將關鍵字以分類 chip / tag 形式呈現，不得把 category 寫死在前端常數裡。
4. 玩家點擊關鍵字後，再進一步點「互動」才觸發 `POST /v1/npc/dialogue`；避免每次選詞都直接打模型。
5. 人物頁 `general-journal-content` 可顯示最近日誌與一句生成反應，但不得取代既有歷史趣聞 / 血脈傳聞。
6. 戰鬥 HUD 頭像點擊可作為未來入口；MVP 先以人物頁練習，降低戰鬥場景風險。
7. Cocos Preview 需設定 FastAPI CORS，開發期允許 `localhost:7456`；正式環境不可使用萬用 `*`。

### H-1. General List 開發測試入口

這是開發中的測試方法，不是最終 UI 版型：在武將列表最上方暫時增加一顆「對話測試」按鈕與一個「關鍵字下拉選單」。

互動流程：

1. 玩家在武將列表點擊某位武將，Cocos 端記錄 `selectedGeneralId`。
2. Cocos 端呼叫 `GET /v1/npc/keyword-options?generalId=<selectedGeneralId>&categories=person,item,event&limitPerCategory=8`。
3. 下拉選單內容改成該武將的可選 keyword；顯示文字用 `label`，送出值用 `keywordKey`。
4. 玩家選完 keyword 後，點擊「對話測試」按鈕。
5. Cocos 端呼叫 `POST /v1/npc/dialogue`，至少帶入 `generalId` 與 `selectedKeywordKeys`；若目前有 context 下拉，也一併帶入 `contextKey`。
6. 回傳後在武將列表上方或人物摘要區顯示 `text` / `line`，並在 debug log 顯示 `evidenceRefs`、`usedKeywords`、`fallbackUsed`。

限制：

1. 這個入口只服務研發驗證，不進正式人物頁視覺定稿。
2. 選武將時才刷新 keyword 下拉，不要在列表初始化時對所有武將批次打 API。
3. 沒有 keyword pack 的武將，下拉選單顯示空狀態；不可前端硬塞測試詞。
4. 按鈕觸發前不得呼叫 `POST /v1/npc/dialogue`，避免每次切換下拉都打模型或消耗中台資源。
5. Cocos component 不直接散落 `fetch`；仍需集中走 `NpcDialogueService`，方便日後把 base URL、timeout、fallback、debug log 統一管理。

2026-05-08 現況：Cocos 端已存在集中式 `NpcDialogueService` 與 GeneralList 對話測試模式，並可切換 `locale`、`speechContextMode`、`llmModelPreset`，顯示 `providerTrace` 與 `qualityWarnings`。缺口是尚未包裝 `GET /v1/npc/context-options`，GeneralList dev toolbar 目前主要以 keyword-only 對話測試為主，後續需補 contextKey 選擇或自動帶入推薦 context。

## I. Data Schema 需求

中台不直接寫入玩家存檔完整向量庫。客戶端只保留摘要、快取與同步指標。


## J. 驗收標準

### J-1. 資料管線驗收

| Gate | 標準 |
|---|---|
| PDF 轉 MD | 可產生 `source.md` 與章回 manifest |
| 清洗 | 頁碼、頁首、頁尾與重複空白被移除 |
| 稱呼消歧 | 類似「將軍，我送您一把寶刀」的對話可在有足夠場景證據時把 `將軍` 解析回正確 `generalId`，並保留物品關係 |
| 抽取 | 張飛長坂橋事件可穩定抽出 `generalId=zhang-fei` |
| 關鍵字分類 | 張飛可穩定抽出人物 / 事件 / 地點 / 物品 / 生物關鍵字，且雜訊詞不進正式 keyword pack |
| 去重 | 同一事件跨 chunk 不重複入庫 |
| 入庫 | Pinecone metadata filter 可按 `generalId + contextKey` 命中 |

### J-2. 對話驗收

| Gate | 標準 |
|---|---|
| 史實吻合 | 台詞可回扣 evidenceRefs |
| 口吻吻合 | 張飛豪烈、關羽沉穩、趙雲忠勇不得混淆 |
| 關鍵字成功 | 玩家點選「劉備」「丈八蛇矛」等關鍵字時，張飛能以自身視角與口吻產生相關聯想 |
| 字數 | 預設 20~60 字，UI 不溢出 |
| 安全 | 不現代化、不亂編重大史實、不破第四面牆 |
| Fallback | 中台故障時 Cocos 可顯示模板台詞 |

## K. 名詞定義

| 名詞 | 代碼 / Key | 定義 |
|---|---|---|
| 三國大腦中台 | `SanguoBrainService` | 三國文本抽取、向量檢索、persona 與台詞生成服務 |
| Corpus | `Corpus` | PDF / Markdown / 正史 / 演義來源集合 |
| Chunk | `TextChunk` | 可向量化的語意片段 |
| Event Key | `contextKey` | 可供玩家下拉選擇與 RAG filter 的事件鍵 |
| Keyword Option | `keywordKey` | 由 ETL 產生、供玩家點擊互動的關鍵字鍵 |
| Keyword Category | `person/event/location/item/creature` | 關鍵字分類 enum；可擴充但不得讓 UI 自行猜測 |
| Evidence Ref | `evidenceRef` | 可追溯到章回、段落或資料源的引用 ID |
| Persona Card | `Npc_Persona_Card` | 武將性格與口吻的結構化描述 |
| Brain Profile | `Brain_Service_Profile` | 當前使用的中台 / 本地 / 離線模式設定 |

## L. 實作路線

1. **現況規格化**：把 server 已完成的 FastAPI facade、runtime profile 消費、provider router、Cocos dev toolbar 與 LangGraph 狀態回寫本規格，避免後續 Agent 重複做已完成的 pilot 工作。
2. **多武將 Readiness**：將 `api-readiness` 從張飛單人報告升級為多武將矩陣，首批以現有 runtime profiles 的十人為準，列出 persona、context、keyword、resolved evidence 與 deterministic dialogue smoke 狀態。
3. **Evidence Resolver 正式化**：從 `NpcDialogueService` 內嵌邏輯抽出 `EvidenceResolver`，輸出 `ResolvedEvidencePack`、`unresolvedEvidenceRefs`、`resolutionTrace`，並落實 keyword evidence 優先於衝突 context 的規則。
4. **Provider / QA 強化**：將 `providerTrace`、`fallbackUsed`、`qualityWarnings`、`repairUsed` 納入 readiness 與 Cocos debug 驗收，避免把 deterministic fallback 誤判為真 LLM 成功。
5. **Cocos Dev Flow 對齊**：在 Cocos `NpcDialogueService` 補 `context-options` wrapper，GeneralList dev toolbar 補 contextKey 選擇或自動推薦 context，仍維持按鈕觸發才 POST dialogue。
6. **互動記憶 M1-M4**：依 `NPC Brain Memory System`（`docs/tech/npc-brain-武將互動記憶系統.md (doc_other_0085)`）先落地 `saveId + generalId` 結構化記憶的 schema、JSONL/JSON storage、memory API、`DialogueRequest.saveId` / `memoryContext` prompt 注入；四段 LLM 壓縮與 Cocos adapter 下一輪再做。
7. **Vector Runtime 接回**：建立 artifact-first + vector-second 的 Evidence Resolver 策略，Pinecone / Qdrant 只在 evidence 不足或需語意召回時介入；SQLite-vec 在完成前不得宣稱為正式離線向量降級。
8. **部署與營運化**：短期使用已驗證的本機 LangGraph dev server + localtunnel；正式 LangSmith Deployments 等 organization 權限解鎖後再推進。`sanguo_etl_graph` 固定輸出 focus generals、bottleneck 與 recommended commands，作為每輪 repair-review campaign 導航。
9. **第二階段能力**：在以上 gate 穩定後，再推 `/v1/npc/dialogue/stream`、vLLM 高吞吐、完整 SQLite-vec 離線快取與正式 GeneralDetail 視覺整合。

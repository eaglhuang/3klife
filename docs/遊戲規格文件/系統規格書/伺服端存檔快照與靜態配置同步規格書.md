# 伺服端存檔快照與靜態配置同步規格書

> **責任邊界**：本檔為伺服器核心表（users / save_snapshots）、雲端快照同步與 CDN 靜態設定檔熱更校驗的單一真相來源。
> **關聯 WBS**：DS-13（Server 資料表與靜態 Config 上 CDN）、DS-11（客戶端 Tx_Hash 雜湊鏈）、DS-12（伺服器事件重演）。
> **整併裁決**：確立 save_snapshots 單一玩家保留最新快照協議；定案客戶端啟動時 CDN MD5 清單增量比對機制。

---

## §1. 伺服端核心資料表結構 (DDL Schema)

雲端存檔服務由關聯式資料庫兩大核心表支撐：

### 1.1 使用者帳號表 (`users`)

```sql
CREATE TABLE IF NOT EXISTS users (
    player_id VARCHAR(64) PRIMARY KEY,
    account_status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE / BANNED / GUEST
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_login_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

### 1.2 雲端存檔快照表 (`save_snapshots`)

```sql
CREATE TABLE IF NOT EXISTS save_snapshots (
    player_id VARCHAR(64) PRIMARY KEY,
    save_version VARCHAR(32) NOT NULL,          -- 嚴格 SemVer 版號 (如 '1.0.0')
    last_sync_hash CHAR(64) NOT NULL,           -- SHA-256 滾動雜湊鏈
    tx_seq BIGINT NOT NULL DEFAULT 0,            -- 單調遞增動作序號 (防重放攻擊)
    snapshot_data LONGTEXT NOT NULL,            -- 加密壓縮之 Root Save JSON
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

> **單一最新原則**：為控制儲存成本並確保還原一致性，每位玩家於線上資料庫**僅保留最新一份有效快照**。歷史回溯日誌由冷備份物件儲存非同步歸檔。

## §2. CDN 靜態設定檔熱更新與 MD5 增量同步

遊戲啟動階段，客戶端透過 CDN 清單進行熱更新校驗，杜絕全量資源無端下載：

```
[客戶端啟動] ──> [請求 CDN config-manifest.json] ──> [逐檔比對 MD5]
                                                          │
  ┌───────────────────────────────────────────────────────┘
  ▼
[MD5 完全一致?]
  ├──> [是: 一致] ──> 直接讀取本地快取，秒進遊戲大廳
  └──> [否: 異動] ──> 僅增量下載變更之 JSON 檔，原子寫入本地儲存
```

### 清單契約結構 (`config-manifest.json`)

```json
{
  "manifestVersion": "2026.11.07",
  "files": {
    "data/generals.json": { "md5": "a8f3b2...", "sizeBytes": 142080 },
    "data/troops.json": { "md5": "c71e04...", "sizeBytes": 12450 },
    "data/gene-dictionary.json": { "md5": "91b2c4...", "sizeBytes": 38900 }
  }
}
```

## §3. 防篡改與事務序號校驗 (Anti-Tamper & Tx_Seq)

客戶端向伺服器同步本機存檔快照時，伺服端執行硬性防禦驗證：

1. **序號單調遞增**：傳入請求之 `tx_seq` 必須嚴格大於資料庫中已記錄之 `tx_seq`（$\text{tx\_seq}_{\text{req}} > \text{tx\_seq}_{\text{db}}$）。
2. **雜湊鏈吻合**：客戶端傳入之起始 Hash 必須與伺服端前次確認之 `last_sync_hash` 吻合。
3. **違規攔截**：若序號倒退或 Hash 分叉，伺服端立即返回 `409 Conflict` 並下發雲端權威快照強制覆蓋，徹底防範離線修改器與 SL 刷數值作弊。

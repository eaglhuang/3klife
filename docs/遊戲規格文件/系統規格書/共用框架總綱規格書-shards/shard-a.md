## 1. 原則與目的

使用者定案：很多系統本質相同，一定要抽出共用 base 框架，各玩法只做**包裝與差異設定**，不准每個單獨寫。共用寫好之後，開新功能會又穩又快。

1. **一個本質一套框架**：買賣就是商店、持有就是庫存、接解任務就是任務、給獎罰就是獎勵、學用技能就是技能、播演出說故事就是劇情（演出）、人被誰占用就是人員占用。
2. **玩法 = 設定 + 薄包裝**：新玩法優先只寫 JSON 設定；需要特殊行為時，只註冊 handler／演出模組／效果種類，不複製框架邏輯。
3. **框架只依賴框架**：玩法依賴框架，框架之間依賴方向固定（見第 6 章），不可反向。
4. **重要數值與結果一律走共用 API**（第 5 章，硬規則）：單機也一樣，由本機伺服器 adapter 實作；日後只換網路 adapter。
5. **舊規格不推翻**：既有專項規格（道具、倉庫、轉蛋、任務、戰法……）降為「某框架的包裝差異設定」，保留其數值與裁決。

分工邊界（避免重疊）：
- 任務只管「接、解、進度、勝敗結算」，獎懲內容交獎勵。
- 獎勵決定「給什麼、用哪種演出」，播放交劇情（演出）系統，入帳交物品庫存。
- 商店只管「定價與成交」，持有交物品庫存，抽獎類商品交獎勵。
- 劇情（演出）系統是播放層：劇情只是用途之一，開寶演出、戰場奧義演出、結業典禮都由它播放。
- 人員占用只回答「這個人忙不忙、被誰占」與互斥判定；各玩法的接取資格（年齡、將階）仍歸各玩法，占用框架不判斷適不適任。
- 轉蛋保留自己的畫面與演出；**抽獎、權重、保底一律由獎勵框架 `reward.roll` 計算**（使用者 11/21 裁決 #9），扣款走商店與錢包，入庫走物品庫存。

## 3. 新增框架的判準與流程

### 3.1 判準
- **兩處以上出現類似功能**就提案；單一玩法獨有的，不提案。
- 提案時要回答：本質是什麼？哪兩個以上現有系統其實在做同一件事？差異可以只用設定表達嗎？
- 不提案的情況：只是同一框架的另一個包裝（例如新商店、新任務種類）。

### 3.2 流程
1. 任何人（企劃或工程）發現兩處類似，在本書第 11 章「候選清單」登記：名稱、兩個以上出處、共同本質、差異。
2. 總 PM 裁決是否成立；成立則由企劃寫一份 `XXX系統Base框架規格書`，格式同六份系統規格書（含「伺服器 API」章）。
3. 登錄 doc-id、更新本書第 2、4、6 章表格與索引，再開實作卡（base 排第一）。

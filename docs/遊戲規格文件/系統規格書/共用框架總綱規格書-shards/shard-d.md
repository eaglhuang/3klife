## 9. 實作卡總順序

家業規格 (doc_spec_1181) 第 14.1 節排的是 B1 庫存 → B2 商店 → B3 任務 → B4 獎勵 → B5 技能 → B6 劇情。本書在「共通 API 層＋本機 adapter＋存檔」之後建議的最終順序如下（與 9199 不同處以粗體標示）：

| 順序 | 卡名（暫） | 依賴 | 理由 |
|---|---|---|---|
| 0 | **API-BASE**：共通 API 層＋本機伺服器 adapter＋存檔走 API＋契約測試＋`check-api-bypass` | 無 | 硬規則；所有框架都依賴，先做才不會寫完又重做 |
| 1 | **FND-BASE**：共通底層工具層（確定性亂數、加權表、條件評估、階梯、時鐘；見第 11 章 Q-A） | 0 | 純函式、工作量小，但獎勵、任務、商店、劇情、技能都要用；先做避免各框架各寫一份 |
| 2 | ITM-BASE（9199 的 B1）：持有者容器、物品定義擴充、資源與貨幣命名統一 | 0、1 | 所有框架的底層；現有 `PlayerInventory` 沒有持有者概念，要先補 |
| 3a | **RWD-BASE（9199 的 B4 提前）**：獎池、保底、等階、懲罰、效果帳本、`settle`（演出先用 `instant`） | 0、1、2 | 任務結算要呼叫獎勵；先有獎勵，任務才不會自己發獎而日後重工。現有任務核心的效果帳本是它的前身 |
| 3b | **SKL-BASE（9199 的 B5 提前並行）**：技能定義、持有、`status-effect` | 0、1、2 | 幾乎無依賴，可與 3a 並行；家業的專長、家風要用 |
| 3c | SHP-BASE（9199 的 B2）：貨架、上下架、折扣、輪替、限購 | 0、2（寶箱商品待 3a） | 只依賴庫存，可與 3a、3b 並行 |
| 4 | **PERSON-OCC：人員占用框架（第 7 框架，使用者 11/21 裁決 #8）**：OCC-M 精簡版已合併（PROG-2-9207），補完與六處遷入見 doc_spec_1242 第 12 章 | 0 | 任務派遣、家業職缺、學府、歷練、出征都要查「這個人忙不忙」，要在任務 base 之前 |
| 5 | QST-BASE（9199 的 B3，**移到獎勵之後**）：定義、條件、進度、solver、結算 | 0、1、3a、4 | 結算依賴獎勵；派遣依賴人員占用 |
| 6 | STY-BASE（9199 的 B6）：劇本層＋演出播放器與佇列＋`chest` 等演出模組 | 0、3a | 獎勵的給獎演出模組與儀式流程；演出播放器介面可在 3a 時先放簡版 |
| 7 | 季結算管線（Q-C，PM 裁決成立，排在 MVP 之後；候選 C） | 0、1 | 家業、學府、季級效果共用 tick；家業 E0 需要 |
| 並行 | 網路 adapter 與 `server/src/api/` | 0 | 以契約測試為準，可與 2～7 並行 |
| 之後 | 各框架遷移卡（依 5.9 優先序）、家業 E0 與其後各批 | 對應框架 | 每遷一個，繞過基準清單就減少 |

原因彙整：(1) 先 API 再框架，因為框架的命令都走 API；(2) 獎勵早於任務，因為任務只管接解與成敗、獎懲內容必須由獎勵給；(3) 技能與商店沒有互相依賴，可與獎勵並行縮短工期；(4) 劇情最後，因為它的給獎演出由獎勵驅動，且演出播放器介面先簡後繁即可；(5) 人員占用（已成為第 7 框架）與季結算，都是任務與家業的前置；(6) 轉蛋抽獎遷移（獎勵書第 12 章）排在獎勵 base 與物品庫存之後。

## 10. 大方向待決題的裁決結果（原「待使用者決定」，2026-11-21 回寫）

標註規則：**使用者 11/21 裁決**＝使用者親自回答；**PM 裁決**＝依使用者已定案大方向由總 PM 定案（不涉及商業化價格與戰場核心規則）。候選框架與底層工具層的題（Q-A～Q-G）見第 11.3 節。

- **Q1 API 層落地順序：** **PM 裁決** A 先做 API 層＋本機 adapter＋存檔走 API，再做各框架 base（B0 已合併，順序成立）。
- **Q2 貨幣是否併入物品庫存：** **PM 裁決** A 併入（`kind=currency`，經 `wallet.*` 命令，錢包碼 E301～E303 已實作）。**使用者 11/21 裁決 #14／#28 補充：金與銀兩是兩種貨幣並存、各有用途，不合併成一種**；詳見貨幣與資源總規格書 (doc_spec_1241)。付費貨幣的商業化與定價仍另題，不在本題。（與庫存書 Q2 同題，以此處為準。）
- **Q3 單機版伺服器側存檔是否與玩家端存檔分檔：** **PM 裁決** A 分開（本機伺服器檔＋檢視快取），日後可直接上傳。
- **Q4 `check-api-bypass` 嚴格度：** **PM 裁決** A 基準棘輪（只減不增），全遷完後轉零容忍。
- **Q5 連線上線時 `critical` 補丁何時全面禁止：** **PM 裁決** A 階段 2（正式上線）才禁止。
- **Q6 劇情（演出）系統名稱：** **PM 裁決** A「劇情（演出）系統」。

### 11.3 待決選擇題的裁決結果（2026-11-21 回寫）

- **Q-A 共通底層工具層（確定性亂數、加權表、條件評估、階梯評估、時鐘）：** **PM 裁決** A 設立。純函式庫位於 `assets/scripts/shared/`（`foundation/` 已落地），零依賴，不算框架、不走命令。
- **Q-B 人員占用登記：** **使用者 11/21 裁決 #8**：獨立成**第 7 個共用框架**（沒有併入任務）。登記表、互斥矩陣、`occupancy.*` API、E33x、網路 adapter 見 `人員占用系統Base框架規格書 (doc_spec_1242)`；OCC-M 精簡版已合併（PROG-2-9207）。
- **Q-C 季結算管線與時間週期：** **PM 裁決** A 成立，但排在一年循環 MVP 之後（學府凍結只有一處）。
- **Q-D 設施等級、聲望階、經驗等級：** **PM 裁決** A 合併為底層工具 `Ladder`。
- **Q-E 通知與信箱：** **PM 裁決** A 先登記為候選，待獎勵溢出轉信箱與遺書信箱實作時再提案。

- **Q-G 資源與貨幣命名統一：** **使用者 11/21 裁決 #14 修正原推薦**：原案「`silver` 登記為 `gold` 別名、兩者視為同一種」**作廢**。新裁決：**保留金與銀兩兩種貨幣**（金＝國家／幕府公庫，銀兩＝家族私房，見 #28），只統一**糧食命名為「糧草」**（PM 定名；規範 id 沿用 `food`，`grain` 為別名，玩家可見名稱一律「糧草」，「糧食」一律改名）。`resource-def.v1` 規範 id 改為 `food／gold／silver／troops／fame`；詳見貨幣與資源總規格書 (doc_spec_1241) 與庫存書 3.5。

### 11.4 結論

六套框架成立、且皆有判定歸屬；使用者 11/21 另裁決**人員占用升格為第 7 個共用框架**；除此之外只有兩項值得獨立（季結算與時間週期，加上底層工具層），其餘候選都已歸入子模組或暫不抽。之後新增框架仍依第 3 章流程。

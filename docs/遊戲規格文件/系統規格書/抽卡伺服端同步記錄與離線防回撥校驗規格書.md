# 抽卡伺服端同步記錄與離線防回撥校驗規格書

## 1. 核心定位與設計理念
本規格書定義三國生活（3KLife）轉蛋系統之「伺服端同步資料結構、抽卡進度持久化與離線防回撥安全校驗」規範（對應 WBS `GCH-14` 與 `PROG-2-1256`）。
轉蛋存檔資料作為攸關玩家核心資產與防作弊治理之重地，堅持**只增不減、強制非負、伺服端權威**原則：
1. **抽數單調遞增不倒退**：客戶端總抽數只能大於或等於伺服端記錄，任何低於伺服端的數據視為時鐘回撥作弊或髒資料。
2. **出金記錄邏輯約束**：最後一次抽出 SSR 名將之抽數記錄絕對不得大於當前總抽數。
3. **無損雙向相容校驗**：離線弱網同步時，嚴密校驗客戶端欄位合法性，校驗失敗或倒退時平滑退回伺服端權威資料。

---

## 2. 轉蛋同步記錄實體結構 (`GachaSyncRecord`)
伺服端資料表（`player_gacha_records`）映射之標準結構定義如下：
```typescript
export interface GachaSyncRecord {
    totalPulls: number;     // 累計總抽數（Total_Pulls）
    pityCounter: number;    // 距上次小保底抽數（Pity_Counter）
    bondingPoints: number;  // 玩家當前結義點數餘額（Bonding_Points）
    lastSsrPull: number;    // 最近一次抽出 SSR 角色時的累積抽數
}
```

### 2.1 抽卡結算組裝 (`buildGachaSyncRecord`)
抽卡完成後，系統依據各池保底狀態與當前錢包組裝同步列：
- $\text{pityCounter} = \text{totalPulls} \pmod{50}$。
- $\text{lastSsrPull} = \text{pityState.lastSsrPull} \mathbin{??} 0$。

---

## 3. 靜態完整性校驗規則 (`validateGachaSyncRecord`)
任何同步列在落盤或反序列化時，均需通過純邏輯檢驗：
1. **非負整數約束**：`totalPulls`、`pityCounter`、`bondingPoints`、`lastSsrPull` 均必須為有限整數且 $\ge 0$。
2. **出金點位邏輯邊界**：
   $$\text{lastSsrPull} \le \text{totalPulls}$$
   若出金記錄大於當前累積抽數，回傳 `lastSsrPull 不可大於 totalPulls`。

---

## 4. 離線對齊與防回撥安全演算法 (`reconcileGachaRecord`)
客戶端在連線重試或登入對齊時，傳入本地記錄與伺服端記錄進行對齊判定：

```typescript
export type GachaSyncResult =
    | { ok: true; record: GachaSyncRecord }
    | { ok: false; reason: 'invalid-client' | 'pulls-regressed'; record: GachaSyncRecord };
```

### 4.1 對齊仲裁決策鏈
1. **客戶端格式檢驗**：
   若客戶端記錄未能通過 `validateGachaSyncRecord`，判定為非法客戶端資料，回傳 `{ ok: false, reason: 'invalid-client', record: server }`。
2. **抽數單調性檢驗（防回撥/存檔倒退）**：
   若 $\text{client.totalPulls} < \text{server.totalPulls}$，代表客戶端存檔遭篡改、時鐘回退或非最新設備，回傳 `{ ok: false, reason: 'pulls-regressed', record: server }`，強制保留伺服端進度。
3. **採納客戶端最新記錄**：
   若客戶端總抽數 $\ge$ 伺服端且格式完整，判定客戶端在離線狀態下合法推進抽卡，回傳 `{ ok: true, record: client }`，伺服端更新至最新進度。

## 5. Unity 與 Cocos Creator 概念對照
| 概念維度 | Cocos Creator 實作架構 | Unity 引擎對照架構 |
| :--- | :--- | :--- |
| **同步資料封包** | `GachaSyncRecord.ts` 純函式驗證與對齊 | C# `GachaSyncPacket` 搭配 protobuf / JSON 驗證 |

## 6. 驗證條件與測試矩陣 (Acceptance Gate)
1. **TC-GCH14-01 欄位非負與邊界校驗**：傳入負數或浮點數，驗證回傳錯誤清單；`lastSsrPull > totalPulls` 驗證被拒絕。
2. **TC-GCH14-02 抽數倒退防護**：伺服端為 100 抽，客戶端傳入 80 抽，驗證回傳 `pulls-regressed` 且資料退回伺服端 100 抽。
3. **TC-GCH14-03 離線正常推進採納**：伺服端為 50 抽，客戶端離線抽至 60 抽，驗證對齊成功採納 60 抽。
4. **TC-GCH14-04 小保底計算精準**：73 抽時計算 `pityCounter`，驗證精準為 $73 \pmod{50} = 23$。

# 武將個性卡規格

## 1. 目的與定位

- `Persona Card` 是 `三國大腦中台` 在接入 Gemini / Ollama / vLLM 之前的 deterministic 中介資產。
- 它的責任不是直接產生最終台詞，而是先把「這位武將能怎麼說、不能怎麼說、目前有哪些已驗證證據」整理成結構化卡片。
- 若用 Unity 類比，`Persona Card` 比較像「對話人格用的 ScriptableObject / Addressable Data Asset」：
  - `build_persona_cards.py` 像 build/import pipeline。
  - `persona-card.response.json` 像 runtime 可直接讀取的序列化 asset。
  - 真正的 LLM 只像 renderer，不是人格資料的唯一真相來源。

## 2. 輸入來源

`build_persona_cards.py` 的正式輸入如下：

1. `assets/resources/data/generals.json`
   - 武將主資料。
   - 提供 `id`、`name`、`title`、`faction`、`rarityTier`、`characterCategory`、`awakeningTitle`、`notes`、`stats` 等欄位。

2. `artifacts/data-pipeline/sanguo-rag/extracted/events/events.jsonl`
   - 已抽取完成的事件候選。
   - 提供 `generalIds`、`sourceRefs`、`relationshipEdges`、`moodTags`、`summary`、`location`、`sourceQuote` 等人格與證據訊號。

3. `artifacts/data-pipeline/sanguo-rag/extracted/keyword-options/{generalId}.keywords.json`
   - 該武將可互動的 keyword pack。
   - 提供 `keywordAnchors`，讓 persona card 知道此武將目前可被問到哪些人 / 事 / 地 / 物。

4. `server/npc-brain/pipelines/sanguo-rag/build_persona_cards.py`
   - 內建兩種規則常數：
   - `PERSONA_PRESETS`：少數核心名將的口吻 / 個性 / taboo / fallback 補強。
   - `CORE_REVIEW_GENERAL_IDS`：核心名將人工抽查名單。

## 3. 事件過濾規則

只有通過下列規則的事件，才允許進入 persona card：

1. `reviewStatus` 必須是 `ready`。
2. `eventType=alias-smoke` 的事件一律排除。
3. 如果 `sourceRefs` 全部都是 `fixture.*`，一律排除。
4. 事件必須在 `generalIds` 中包含目標武將，才會被歸到該武將名下。

這代表 persona card 只收正式證據，不收 schema smoke / alias smoke 這類測試或管線檢查資料。

## 4. 欄位生成規則

| 欄位 | 生成規則 | 來源檔 | 備註 |
|---|---|---|---|

| `personaVersion` | 固定寫死 `general_persona_v2` | `build_persona_cards.py` | schema version；v2 明確以 `edgeConfidence` / `edgeStrength` 描述 relationship anchors |
| `generatedAt` | `utc_now()` 動態產生 | `build_persona_cards.py` | build timestamp |
| `displayName` | `general.name`，缺值才回退 `general_id` | `assets/resources/data/generals.json` | 顯示名 |
| `title` | `general.title`，若無則取 `awakeningTitle`，再去除 `【】` | `assets/resources/data/generals.json` | 經 `normalize_title()` 處理 |
| `faction` | 直接取 `general.faction` | `assets/resources/data/generals.json` | 陣營 |
| `sourceProfile.rarityTier` | 直接取 `general.rarityTier` | `assets/resources/data/generals.json` | 來源摘要 |
| `sourceProfile.characterCategory` | 直接取 `general.characterCategory` | `assets/resources/data/generals.json` | 來源摘要 |
| `sourceProfile.awakeningTitle` | 直接取 `general.awakeningTitle` | `assets/resources/data/generals.json` | 來源摘要 |
| `sourceProfile.notes` | 直接取 `general.notes` | `assets/resources/data/generals.json` | 來源摘要 |
| `voiceStyle` | `PERSONA_PRESETS.voiceStyle` + `derive_generic_traits()` 推導出的 voice，最後 `unique()` 去重 | `build_persona_cards.py` + `assets/resources/data/generals.json` + `events.jsonl` | 保留順序，先 preset 後 derived |
| `personalityTraits` | `PERSONA_PRESETS.personalityTraits` + `derive_generic_traits()` 推導出的 traits，最後 `unique()` 去重 | `build_persona_cards.py` + `assets/resources/data/generals.json` + `events.jsonl` | 保留順序，先 preset 後 derived |
| `relationshipAnchors` | 彙整 `relationshipEdges` 中與該武將相連的 edge；若該武將是 `toId`，type 會加上 `reverse:` 前綴 | `events.jsonl` | 目前依 `edgeConfidence` 排序；`edgeStrength` 為可選語意強度欄位 |
| `keywordAnchors` | 讀取 `{generalId}.keywords.json`，排除 `retired`，依 `confidence desc / category / keywordKey` 排序 | `keyword-options/{generalId}.keywords.json` | 最多 12 筆 |
| `moodAnchors` | 彙整所有事件的 `moodTags`，再 `unique()` | `events.jsonl` | 不排序權重，只保留首次出現順序 |
| `evidenceRefs` | 聯集所有事件的 `sourceRefs` 後排序 | `events.jsonl` | persona card 的最終證據索引 |
| `safeFallbackLine` | 先取 `PERSONA_PRESETS.safeFallbackLine`，沒有 preset 才用預設模板 | `build_persona_cards.py` | 給 runtime / LLM fallback 用 |
| `taboos` | `PERSONA_PRESETS.taboos` + generic taboos，再 `unique()` | `build_persona_cards.py` | generic taboos 固定包含不可自稱 AI 等限制 |
| `llmPromptRules` | 固定三條 prompt 規則 | `build_persona_cards.py` | 規範 LLM 只能用 persona + evidence |
| `manualReviewRequired` | `general_id in CORE_REVIEW_GENERAL_IDS` | `build_persona_cards.py` | 人工抽查 gate，不是內容來源 |

## 5. derive_generic_traits() 推導規則

`derive_generic_traits()` 目前採「名冊數值 + 事件 moodTags」雙來源合成：

1. `str >= 80`
   - traits 加入 `勇武`
   - voice 加入 `有武將氣勢`

2. `int >= 85`
   - traits 加入 `多謀`
   - voice 加入 `善於權衡`

3. `pol >= 85`
   - traits 加入 `重政略`

4. `cha >= 85`
   - traits 加入 `有號召力`

5. 事件 `moodTags`
   - 先做頻次統計，取前 3 名加入 `personalityTraits`

6. 保底規則
   - 若完全推不出 traits，補 `謹慎應對`
   - 若完全推不出 voice，補 `符合三國語境`

7. generic taboos
   - 固定加入：
   - `不得自稱 AI`
   - `不得新增未提供 evidence 的重大史實`
   - `不得使用現代網路語`

## 6. 生成流程

`build_persona_cards.py` 的實際流程如下：

1. 讀取 `generals.json`，選出 `--general-id` 指定的武將，或全部武將。
2. 讀取 `events.jsonl`，依事件過濾規則先清掉 alias-smoke 與 fixture-only 事件。
3. 依 `event.generalIds` 把事件索引到各武將名下。
4. 對每位武將：
   - 讀取該武將的 keyword pack。
   - 讀取該武將在 generals.json 的 profile。
   - 執行 `derive_generic_traits()`。
   - 套用 `PERSONA_PRESETS`。
   - 組成 `PersonaCard`。
5. 輸出：
   - 每位武將一張 `{generalId}.persona.json`
   - `persona-cards.index.json`
   - `persona-cards-summary.md`

## 7. 核心六名將的特殊規則

目前以下六位會被標成 `manualReviewRequired=true`：

- 張飛
- 關羽
- 趙雲
- 劉備
- 曹操
- 諸葛亮

這個標記的意義是「先進人工抽查流程」，不是說整張卡都是手工寫死。

### 7.1 哪些部分是寫死的

這六位目前只有下列欄位是透過 `PERSONA_PRESETS` 明確指定：

- `voiceStyle`
- `personalityTraits`
- `taboos`
- `safeFallbackLine`

### 7.2 哪些部分不是寫死的

即使是這六位，以下內容仍然是資料驅動：

- `displayName`
- `title`
- `faction`
- `sourceProfile.*`
- `relationshipAnchors`
- `keywordAnchors`
- `moodAnchors`
- `evidenceRefs`
- `generatedAt`
- `manualReviewRequired` 以外的流程輸出

換句話說，這六位不是「整張 persona card 寫死」，而是「核心人格語氣有 preset，其他欄位仍由名冊 / 事件 / keyword pack 生成」。

## 8. Pilot Seed 與正式流程分工

### 8.1 目前的 `changban-bridge` gold seed 是什麼

- `changban-bridge` 目前已收斂為 `gold_seed_registry.py` 內的 hand-authored `gold seed spec`，再交給 `build_gold_seed_battle_event()` 與通用 `extract_battle_cluster()` 萃取 battle cluster。
- 它的用途是先提供一個高信心、可人工審查、可回歸測試的標準事件，讓 `events -> keyword pack -> persona card -> API -> Cocos` 這條鏈先打通，同時把「seed 定義」與「battle cluster 抽取」拆開。
- 它不是正式版要大量複製的事件生產方式。
- 若用 Unity 類比，它比較像一個「手工標好的黃金 ScriptableObject 測資」，用來驗證 importer、schema、runtime 與 UI 是否一致。

### 8.2 為什麼現在可以手工寫 `intimidates / protects` 與 `0.9 / 0.86`

- 目前這段資料的角色是 `deterministic pilot seed`，不是最終的全量歷史真相。
- `RelationshipEdge.edgeConfidence` 的語意是「抽取信心 / extraction confidence」，不是「仇恨值 / 保護值 / 關係強度」。
- 因此：
  - `zhang-fei -> cao-cao / intimidates / 0.9`
    - 表示「目前 pipeline 有 0.9 的把握，這段文本可抽成 intimidation 關係」。
  - `zhang-fei -> liu-bei / protects / 0.86`
    - 表示「目前 pipeline 有 0.86 的把握，這段文本可抽成 protect 關係」。
- 它不表示「張飛的敵意值 = 0.9」或「保護欲 = 0.86」。

### 8.3 為什麼要拆成 `edgeConfidence` 與 `edgeStrength`

舊版曾把「抽取信心」和「關係強弱」混在同一個 `confidence` 欄位，容易誤導下游把它當人格參數；目前已拆成 `edgeConfidence` 與 `edgeStrength`。

正式版建議拆成：

1. `edgeConfidence`
   - 抽取器對這條 edge 是否成立的信心。
   - 用途：schema gate、review queue 排序、是否進正式 persona card。

2. `edgeStrength`
   - 關係語意本身的強度估計。
   - 用途：未來若要做角色互動權重、記憶偏好、對話優先級，可以用這個欄位，但不能和抽取信心混用。

建議結構：

```json
{
  "fromId": "zhang-fei",
  "toId": "liu-bei",
  "type": "protects",
  "edgeConfidence": 0.86,
  "edgeStrength": 0.92,
  "evidenceRefs": ["042#p1", "042#p2"]
}
```

其中：

- `edgeConfidence` 可由規則 / LLM 提案 / review 結果產生。
- `edgeStrength` 若沒有足夠依據，可先留空，避免為了數值化而偽精準。

### 8.4 哪些 event builder 可以保留成 gold seed

正式版不應該為每個歷史事件都手寫一個 `build_xxx_event()`；但仍應保留少量 hand-authored `gold seed spec` 作為 `gold seed / regression fixture`，並交由通用抽取器組裝成事件。

gold seed 資料應集中在 `gold_seed_registry.py`。`extract_event_candidates.py` 只負責讀取 registry、組裝 battle cluster、輸出 ready event 或 review queue。

建議可保留的類型：

1. 高價值主線戰役樣本
   - 例如 `changban-bridge` gold seed spec。
   - 用來驗證 battle 類事件的 participants、location、moodTags、relationshipEdges、keyword 投影是否正確。

2. 高價值對話互動樣本
   - 例如「稱呼 + 物件 + 對象」這類明確對話事件。
   - 用來驗證 `offered_to`、`advises`、`requests` 類型的 edge。

3. 名稱召回 / alias smoke 樣本
   - 用來驗證 alias recall 與 roster mapping。
   - 這類樣本可保留，但不應直接參與正式 persona card 的人格歸納。

4. 容易誤判的反例樣本
   - 例如同名人物、泛稱、模糊稱呼、未消歧 participant。
   - 用來保證抽取器不會為了完整事件而亂綁 `generalId`。

gold seed 的原則是：

- 少量、代表性強、可人工核對。
- 用於 regression，不用於取代全量事件生產。
- 每一類事件家族保留少數 canonical sample 即可，不做「一事件一函式」全覆蓋。

### 8.5 正式版通用事件抽取器應怎麼接 LLM + review queue

正式流程應該是「通用抽取器為主、少量 gold seed 為輔」，而不是「全部事件都手寫 builder」。

目前 `extract_event_candidates.py` 已有第一版 `generic-battle-candidate-v1`：

- 它依 `sourceRef` 分組掃描 observed mentions。
- 只挑 resolved mentions、至少 3 位參與者、且具有戰事訊號詞的段落。
- 輸出到 `artifacts/data-pipeline/sanguo-rag/extracted/events/generic-battle-candidates.jsonl` 與 review markdown。
- 所有 generic candidates 預設都是 `reviewStatus=needs-review`，不直接進 `events.jsonl`、keyword pack、persona card 或 API readiness。
- generic candidates 暫不填 `location`，避免把未審核的地名 regex 噪音包裝成事實。

建議正式流程：

1. `observed_mentions`
   - 從文本 chunk 抽出人名、地點、物件、稱呼、scene participants。

2. `dialogue_resolution`
   - 先把 speaker / addressee / item interaction 等能 deterministic 解掉的部份解出來。

3. `generic event candidate extractor`
   - 根據 chunk、participants、verbs、location、source quote，自動提出 `EventCandidate` 與 `RelationshipEdge` 候選。
   - 這層應是正式量產主力。

4. `LLM proposer`
   - LLM 可參與下列任務：
   - 建議 event summary。
   - 建議 relationship type。
   - 建議 moodTags。
   - 建議 `edgeStrength` 或摘要標籤。
   - 但 LLM 只能提案，不能直接定案 canonical `generalId`、最終 edge、最終 persona。

5. `schema gate + deterministic validators`
   - 驗證欄位完整性、ID 合法性、sourceRefs 是否存在、participants 是否已消歧。
   - 失敗就退回 review，不得直接進正式 persona card。

6. `review queue`
   - 低信心、矛盾、多人名混淆、edge 類型不穩定的候選，進 review queue。
   - 建議至少拆成：
   - `pending-events`
   - `pending-edges`
   - `accepted-events`
   - `rejected-events`

7. `accepted events`
   - 只有通過 gate 與 review 的事件，才寫入正式 `events.jsonl`。

8. `keyword pack projection`
   - 從 accepted events 投影 `keyword-options/{generalId}.keywords.json`。

9. `persona card aggregation`
   - 從 accepted events + keyword pack + roster profile 聚合 `relationshipAnchors`、`moodAnchors`、`keywordAnchors`。

10. `runtime LLM rendering`
    - runtime LLM 只根據 persona card + retrieved evidence 生成台詞。
    - 不可在 runtime 臨時重寫 persona card 或新增未經驗證的重要關係。

### 8.6 LLM 在正式流程中的正確角色

LLM 應做的事：

- 幫忙讀劇情。
- 幫忙提出候選事件與關係。
- 幫忙補摘要、情緒標籤與語氣建議。

LLM 不應做的事：

- 直接決定 canonical `generalId`。
- 直接把未驗證關係寫進正式 persona card。
- 在 evidence 不足時自由發明人格結論。

因此正式系統的設計原則是：

- `LLM = proposer / renderer`
- `schema gate + review = judge`
- `persona card = approved memory boundary`

## 10. 實務解讀

- 張飛這張卡不是整張手寫，而是：
  - 名冊提供身份骨架。
  - 長坂橋事件提供關係、情緒、證據。
  - keyword pack 提供可互動主題。
  - preset 只補強「核心名將應該怎麼說、不能怎麼說、fallback 怎麼收」。

- 因此後續若擴張更多章回：
  - 先補事件品質與 keyword 投影。
  - persona card 會自然長出更多 `relationshipAnchors`、`keywordAnchors`、`moodAnchors`。
   - 不需要每位武將都人工手寫整張卡。
   - hand-authored event builder 只保留少數 gold seed，正式量產仍以通用抽取器 + review queue 為主。

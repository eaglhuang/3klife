# R5F-B03 保留 ID 與傳星

本規格處理一胎最多六個 held ID、唯一保留保證、一次傳星及真親本因子連代。R5F-B03 不是正式 ATM 工單；全部工作文件與逐功能規格完成前不得開始程式，且真 consumer／准入未核，implementationReady=false。

## 目的 非目標與 owner

玩家可在合法來源中選一個優先延續的 ID，但不能因此保星、直接啟用或增加槽位。責任 owner 為出生 carrier／傳星與 FamilyLineage 能力；B06 持有胎次提交權，B07 擁有效果投影與出生後取得檢查，B08／G03 擁有後天形成／研習事件。實際維護者和 codepath 待核，本文不宣稱已有接線。

非目標：本功能不加 P、不決定婚配對象、不把文化師承算生物親子、不將母門／復興提案當免費第二保證，也不實作研習或媒介取得。

## 流程與數值

1. 先檢來源、choice 及所有必需規則，無效不耗成本或 RNG。R3 父母保證要求指定父或母實際持有、可傳且已知的 ID；不可把祖輩默認套入此保證。
2. carrier 按 sourceUID+canonicalID 去重，以最近深度各抽一次。父母入池1、祖父母.5、曾祖父母.25。這不是 H 深度權重，不把兩者乘成一次。
3. 合法保留 ID 必入池且占一槽。其他入池來源同 ID 依最高 level、最淺depth、穩定sourceUID選唯一來源版；不同 ID 不合併。
4. 將保留 ID 從普通池移除，剩餘按 level/Max 權重、canonicalID 穩定排序不放回，抽至總 held6 或池耗盡。未選保留則六槽皆普通；空池可零個，不補造。
5. 每保留 ID 用 stars.factorID 抽一次星核，超字典 Max 的質量併 same，不越界／不重抽。基礎 Max5 核 down=[0,.10,.10,.15,.15]、up=[.15,.15,.12,.05,0]、same=1−down−up，來源為工程§19。符合 n5 時，星級1–3的 up 各+.05；星級4的+.02或+.04屬待選 profile，未採不能混表。Max3 因子需自己的合法邊界，不照Max5抽五星。
6. 在選定單一真親本與連續相同 canonicalID 的證據下更新 FamilyLineage；不能合併父親較長 streak 與母親另一 root。中斷／媒介／收養不補生物邊，改姓不清原歷史。實際起始 streak與缺位重啟編碼須同版來源明列，不從UI代數猜。

n5 代表五條真親子邊、至少六位人物，不是第五人或第五個主題季。用於本胎星核的資格須從鎖定親本來源取得，不預借子代將成立的 n+1。既有合法家史可先具資格，不硬等教學到第五代。

家傳命名／開宗一次獎勵以 rootUID+canonicalFactorID+rewardKind 等版本化業務鍵去重；多分支同根同 ID 不各領一次，重讀不再命名發獎。R3T58 歷史期望「首次n5券2及命名一次」屬待替換C類，保一次性語義，不把2券當R5已定價格或保證加星。新獎勵金額須明定獎勵profile與相關資訊供需決策。

## 母門與缺位復興邊界

母門來源候選限母／母母／母母母的合法三代鏈。外祖父可在普通祖位，不因外家名稱另得保證。復興需真合法窗、雙親缺位等明列條件；不能永久留祖母五星、不保底2星、不沿用已斷n5。家傳、兼收、母門、復興同時要求保證應拒，不能暗選一項或增加第七槽。是否保留原免費家傳、祖輩是否繞入池與費用／席位／工時，均待 DEC-R4-02。

## 錯誤 保存 遷移與 UI

SOURCE_INCOMPLETE 用於無真來源、缺lineage證據；PROFILE_UNSUPPORTED用於缺策略／星核；STATE_CONFLICT用於同胎多保證或槽衝突；REVISION_CONFLICT用於來源與婚約不同。保留舊結果與來源，不自動降級成普通抽選。pending 查 C03 commit marker，同胎結果不能換seed重抽。

保存 sourceRevision、pool／slot／star流結果、FamilyLineage與命名獎勵鍵的核心引用。父母在婚約後形成／研習升星不回改本胎。legacy 的舊保星、星級與命名獎勵紀錄保原版；新費用不能追扣舊免費保留。n5資料缺失不從同姓或連續畫面補造。

UI 分列「保障ID」「星級仍會變動」「是否已知／啟用」；顯示被替換的唯一保障與合法成本，不顯第七格。未知來源無權顯星或root細節。命名重開可展示已領結果，不能呈新可領按鈕。

### 共通重入順序

讀取既有提交紀錄先於新命令准入：同key與同payload已提交，或同businessEvent已有一致結果，先返回原結果，即使請求帶舊expectedRevision也不重新結算；同key異payload仍拒衝突。只有確定沒有既有提交的新操作才驗expectedRevision、資源與資格。唯讀功能不因此取得寫入權，pending先查commit marker，不換seed或key刷結果。

# R5F-B10 季度配偶候選與 NPC 配對

本規格管理固定世界季度的候選名單及NPC婚配排程。它不是季間補入家族或復活舊敵，後者屬S06。R5F-B10為文件功能索引，非正式ATM工單；全域文件先行閘門、真consumer與正常准入未核，implementationReady=false。

## 目的 非目標與 owner

每世界季度只產生一次可核候選與配對結果，每人最多一組，先驗保留比例、禁親、成年、有效婚姻、同意、孕期與冷卻。玩家拒絕或解雇不即時重抽供給；unknown族譜不當無共祖。owner是季度人口候選／配對協調者，B06接受合法婚約，B01/B04提供來源與親緣檢核。

不創造不明父母的「乾淨」配偶，不保證每個人每季都能成婚，不繞孕期／冷卻補人口，不重生已死人物，也不按隱藏LUK或P替玩家排序。季間新家族、勢力重建、戰略難度與地盤補給不在本功能。

## 來源與已知缺口

[R4 工程](../../publication_candidate/11_R4歷史基線_工程驗收.md) §4/6/13/20、§27 R3T30、§28 R3T31、§35 R4E21–22；[R4 玩法](../../publication_candidate/10_R4歷史基線_玩法.md) §3、§14–15；[R5 模組01](../../publication_candidate/01_共同身份_時間與存檔契約.md) 時鐘分型、[模組02](../../publication_candidate/02_出生_血統與聯姻.md) 真來源與禁親；[模組08](../../publication_candidate/08_決策_衝突與擴充邊界.md) C05／C14與DEC-R5-S06；[模組09](../../publication_candidate/09_證據來源與驗收索引.md) 消費者未核界線。

R3T31原文要求「每人最多一組、保留比例、禁親及冷卻先檢」，本包沒有保留比例、冷卻長度、配對權重的完整值表，不能猜50%或一季。玩法§14每季度外來名單最多4人是歷史候選供給上限，不等NPC配對只能4組，也不等每季一定補滿4人。

## 輸入 輸出與建議 schema

以下為規格介面提案，非現行程式。

| 結構 | 欄位 | 約束 |
| --- | --- | --- |
| QuarterMatchInput | worldQuarterIndex、populationRevision、candidatePolicyRef、pairingPolicyRef、reservationPolicyRef、cooldownPolicyRef、profileHash | policy缺值不可用最近表補 |
| CandidateRoster | rosterId、quarter、candidateUIDs、arrivalSeq、sourceTemplateRefs、publicProjectionRef、status | 同季固定；拒絕／解雇不產新名單 |
| PairingPlan | quarter、orderedPairs[{personAUID,personBUID,eligibilityEvidence}]、excludedReasons、populationRevision | 任一UID最多出現一次；配對次序固定可重播 |
| QuarterPairCommit | businessEventId、payloadDigest、expectedRevision、reservedPeople、conceptionRefs、results、commitMarker | 同quarter同scope一次；不是只靠客戶端key |

輸入需世界人口真UID、生死／婚姻／同意／孕期／冷卻／保留狀態、公開知識、完整祖譜及合法模板來源。輸出是固定名單、配對／未配對原因與合法婚約事件，不是新人物出生結果。

## 流程

1. 以worldQuarterIndex觸發，先查同quarter/scope既有commit。已完成則回原結果；resultPending先恢復，不能建立第二名單。
2. 核policy、人口revision與固定候選來源。候選產生後保arrivalSeq與UID；模板若會建立新人物，須其正式來源／UID創建契約，不在本稿自行造親本。
3. 先移除死亡、未成年、婚姻／同意不符、懷孕／冷卻、被保留的人物。18歲成年為R4同profile基線；保留比例和冷卻必讀明定policy。
4. 以B01/B04檢配對禁親與完整度；unknown不得以O／D20通過。沒有合法配偶可留未配對，不硬湊一組。
5. 依明定穩定排序／權重產配對plan，逐人占用，一人最多一組。確切配對目標與隨機選取率需同profile；本稿不發明最高EP策略。玩家候選排序只用公開欄位與arrivalSeq／UID破同分。
6. 提交前重新驗新提交的populationRevision及占用，避免另一流程已婚／死亡／預約而仍成婚。每對交B06共同婚約檢查，並以同一季度事件協調保留與婚約結果。批次全有／全無或逐對可恢復策略需正式政策，不可部分完成後無記錄整季重跑。
7. 保存名單、排除原因、配對結果與業務鍵。下一真正世界季度才可能產生新名單；主題seasonId切換不是新季度。

## 邊界與退路

同一人可能被兩家／勢力引用，但只有一個personUID與一個配對占用。玩家與NPC同時確認需共同占用檢查，不各自認為人可用。完整來源且不同姓不保證無共祖；同姓亦不直接等近親。

無成年配偶、全unknown或全冷卻時，UI可提供查譜、已核完整來源模板、收養／招募或等待等合法退路。收養不改生物父母／P，也不自動滿足婚配資格。每季四名獨立founder的LUK70至少一人機率59.04%只是歷史抽樣比較，不表示必得高LUK或以隱藏LUK挑人。

## 錯誤 恢復與保存

缺policy回PROFILE_UNSUPPORTED；缺真祖源回SOURCE_INCOMPLETE，保可公開缺件類別。新提交revision或占用衝突回REVISION_CONFLICT／STATE_CONFLICT，讀新狀態再做新合法plan，不改原已提交婚約來源。無效不耗成本或RNG，不因一配對失敗重抽整季名單。

同鍵同payload或已完成季度businessEvent先返回原結果，異payload拒衝突；只有新提交才驗expectedRevision。pending先查marker與已完成對列表，不能因逾時認為全季未執行。保存世界季度、名單UID／arrivalSeq、policy版本、保留及冷卻證據、配對／婚約引用；不只留計數。

legacy已存在夫妻／孕期保原，不以新保留比例拆婚。未知冷卻不當0；舊檔沒有同季名單應標遷移缺口，不能每開畫面生成一次。跨季保持既有人物及同quarter去重，S06新家供給需另一事件與明確來源。

## UI

展示當季名單截止狀態、公開資格和不能配對的可知原因，拒絕後保持同一名單；無候選不偽裝正在無限刷新。未查LUK不進排序、推薦、按鈕、EP精確破同分或tooltip。禁親與風險第一代就告知，不因教學章節鎖住提示。

### 共通重入順序

讀取既有提交紀錄先於新命令准入：同key與同payload已提交，或同businessEvent已有一致結果，先返回原結果，即使請求帶舊expectedRevision也不重新結算；同key異payload仍拒衝突。只有確定沒有既有提交的新操作才驗expectedRevision、資源與資格。唯讀功能不因此取得寫入權，pending先查commit marker，不換seed或key刷結果。

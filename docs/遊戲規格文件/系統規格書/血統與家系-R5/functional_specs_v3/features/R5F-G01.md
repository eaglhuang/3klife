# R5F-G01 共享培育回合功能規格

## 文件狀態與責任邊界

- 文件版本：2026-11-03，逐功能規格 v3。
- specificationStatus：CONTENT_REVIEWED_WITH_OPEN_DECISIONS。
- implementationReady：false。必須先完成全部工作文件、功能清單及全部範圍內獨立功能規格，之後才評估相關決策、真 consumer 與正常施工准入。
- implementationStatus：NOT_VERIFIED；productConsumerStatus：NOT_RECHECKED；testExecutionStatus：NOT_RUN；acceptanceStatus：NOT_ASSESSED。
- formalDocId：null；formalTaskId：null。R5F-G01 是文件功能索引，不是 ATM 工單或產品開工許可。
- 規格責任 owner：模組 03 的培育回合結算；實際產品 owner、caller、檔案路徑與准入均待核。

本功能把一個學院 run 的五維進度、精力、主行動及事件預算當作同一筆有限資源。其完成分母是唯一入學建立、啟動與單回合驗證、計算及原子提交，不能把童年、教官 TP 或畢業選擇的完成度再算一次。

## 目的與非目標

玩家每回合選訓練、休息或明列事件，得到可以解釋、保存及回放的結果；五維共享 36 個主行動。P 固定，A 不超 P，成熟型不懲罰學院效率。

不產生出生 P、不負責童年 A0、不另造母門或研習的免費回合、不實作技能購買、不選畢業候選、不決定主題季跳時。27 訓練 9 休息是特定資源下可構造上界，不是所有玩家的必要排程或所有排列皆可行。

## 輸入輸出與建議 schema

入學輸入是人物身份、認可 A0Revision／A0及P、入學教官卡組、資格／候選數證據、profile與expectedRevision；回合輸入是已入學 active run、認可 A0/L、五維 C、精力、回合、模式、入學教官卡組與當次一位教官、行動與權重、事件 catalog、expectedRevision 及業務事件鍵。輸出包括新 C/A、精力與回合、成功或合法失敗、TP 子帳、事件額度、raw/applied/overflow、提交狀態與可公開摘要。

以下是建議模型，不是現行產品 API；欄位型別須由 C01 驗證。

```text
TrainingRun {
  runId, personUID, profileHash, dictionaryVersion, rngVersion,
  a0Revision, A0Ticks[5], LTicks[5], progressFraction[5],
  trainingTurn: 0..36, stamina: 0..100, mode: manual|auto,
  mentorDeckRefs, admissionEventId, activationEventId,
  eventCatalogVersion, eventProgressSpent: Fraction,
  status: admitted|active|completed_candidate, revision
}
TurnIntent {
  runId, actionEventId, expectedTurn, expectedRevision, payloadDigest,
  action: train|rest|catalogEvent, primaryTrait, weightsFraction[5],
  selectedMentorRef, eventRefs, idempotencyKey
}
TurnReceipt {
  actionEventId, preRevision, postRevision, outcome, resultRef,
  costLedger, tpReceiptRef, rawGain[5], appliedGain[5], overflow[5],
  eventBudgetDelta, committedMarker
}
```

P=20×Talent 的歷史映射中 P 為能力點，每點 10000 ticks；P1600 是 16000000 ticks。五維固定 STR/INT/LEA/POL/CHA。L=P−A0，不以顯示 A 或 ppm 回推。Fraction 約分，0 為 0/1；分子、分母各最多 256 個十進位數字，分母正值。

## 入學建立與啟動的唯一責任

G01 是 R4 工程 §6 admitTraining 的唯一寫入 owner；G02 提供候選數、同人資格及既有 A0Revision 證據，只引用 G01 的入學結果，不另建一份 run。G05 以同筆 admission receipt 初始化 TP／技能子帳，不獨立再建 run。

1. 先查 admissionEventId／冪等鍵及人物入學業務事件已有結果。重送返回原 runId 及目前狀態，不因已有 active run 而拒絕成功重送，更不能把其進度歸零。
2. 對全新入學請求，驗人物至少15歲、在世且HP>25、profile與字典／事件catalog完整、無另一本人 admitted 或 active run；結合 G02 證據核最多三份run候選及合法狀態。G01不自行累計新的auto解鎖人數。
3. 首份run讀認可童年A0Revision與P，凍結A0及L=P−A0。後續run必引用同一認可A0Revision，不能把上次未選候選A當新A0，也不能由介面A回推L。P/A0缺項、不同版或A0>P拒絕。
4. 驗並凍結入學教官卡組1–6張的來源revision；當次可不派教官，但不能省略必要卡組資料或培育中暗加卡。將入學profile、事件catalog與保證靈感所需完整catalog引用一併凍結；若本profile宣告保證靈感而缺其規則，整次入學拒絕，不先產生半份run。
5. 建立唯一 admitted run：stamina=100、五項C各為精確0/1、trainingTurn=0、eventProgressSpent=0/1、TP=0、空回合／事件使用帳與空TP receipt帳；靈感reservation僅依G05已採catalog建立，不能把「空帳」當已領保證靈感。這些是新run初始化，不是load或重送時的reset。
6. admitted→active 的啟動核同一run、固定快照及子帳已完整提交，保存唯一activationEventId後只變更狀態，不重新初始化C、TP、精力或卡組。已active重送啟動回原結果；completed／selected不得以啟動命令退回active。只有active接受applyTurn。
7. 入學建立／啟動均透過C03原子提交。無效入學不建立run、不占新名額、不耗世界季度或RNG；完成run的世界季度成本仍由其唯一完成事件處理，重送入學不能再收或退這筆成本。

## 回合流程與計算

1. 驗 run active、人物可用、expectedTurn/revision 一致、尚有主行動、profile/catalog 完整、權重各非負且總和≤1。未知教官 Rank 或未映射事件拒絕，不取最近值。
2. 訓練前 stamina<20 時拒絕，不扣資源、不抽 RNG。合法訓練先固定當次資料；stamina≥40 的失敗率為 5%，20–39 為 20%。成功 outcome=1，合法失敗 outcome=0；兩者均扣 20 精力與一回合。
3. 休息只扣一回合，回復 50 精力至 cap100；不抽失敗、不給 TP。明列事件依同版 catalog 決定主行動及成本，不接受任意 freeGain。
4. 訓練效率 u=autoMultiplier×min(2,(1+mentorBonus)(1+synergyBonus)(1+eventBonus))。manual=1，auto=.7，僅乘一次；mentor/synergy 在合法 0..1，event 在 −1..1。已知無加成可為 0，資料缺失不可為 0。
5. 每維 rawΔC=.05×u×outcome×w；C'=min(1,C+rawΔC)。把接受值與丟棄 overflow 分開，不銀行、不轉移到別維、不帶入下一 run。
6. 主行動後才依 priority/eventID 結算合法事件。五維共享每回合 .02、每 run .10 的事件進度上限；先限事件預算，再限各維剩餘 C，只扣實際接受進度。.10 是 guard，不能另送 .10。
7. G05 回傳同一 actionEventId 的 TP 與靈感意圖。manual 第 12 回合鼓舞與第 24 回合考核須依該 catalog 唯一事件；auto 不觸發這兩事件或事件覺醒。
8. 精確 C 提交後投影 A=A0+LC；C<1 向下取整至 ticks，C=1 直接 P。一起保存結果、資源與 RNG witness；第 36 回合完成只產生一份 completed_candidate 與一次世界季度結算。

## 邊界 錯誤與恢復

- 15 歲以上且 HP>25 才可入學；18 歲成年婚配／出仕另檢。入學不是成人行為豁免。
- 一個人物同時最多一個 active run；多 run 同一認可 A0，由 G02 管理最多三份候選。不從上一份未選 A 接著增長。
- 28T8R 需要 560 精力而最多供給 500，拒為可行計畫；27T9R 還需逐回合次序驗證。五項各 20 次需要 100 個主行動，不能標成 36。
- VALIDATION_ERROR、UNIT_MISMATCH、SOURCE_INCOMPLETE、PROFILE_UNSUPPORTED 均在抽樣前拒絕。合法失敗不可冒充無效輸入退款。
- REVISION_CONFLICT 要求回讀新狀態，不以新 seed 重跑。同鍵異 payload 回 IDEMPOTENCY_CONFLICT；同業務事件換鍵也不可多領。
- RESULT_PENDING／STORAGE_FAILURE 時保留結果及成本意圖，先查 committed marker；已提交回原 receipt，未提交恢復原交易，未判定前不得退款或再次抽樣。

## 保存 遷移與重入

保存完整 C、A0Revision、profile、事件已用鍵、RNG 版本、進度及 TP receipt 引用。顯示 ppm、動畫完成與 UI 已讀狀態不作結算來源。存檔引用未閉合不切換指標，保上一可用槽。

舊 run 維持原 profile 的 A0、P、C 與成本史。缺 C 的舊檔不可由 A 反推偽造精確進度；只能保 legacy 讀取或提出有來源的遷移方案。換主題季不重置回合、不送精力、不免費完成 run；若要跳世界季度，交由已採時間政策逐項處理。

## UI 與可觀測性

顯示剩餘主行動、精力、模式、合法教官與成功條件；預覽可以說「資源不足」並列可公開原因。未知 P 時透過 U01 輸出公開區間，不同時露精確 A0/L/C/delta 讓人反推。TP、精力、行動成敗可按知識契約精確顯示。

每次結算可追 actionEventId、profileHash、成本、接受與溢出，但 seed、隱藏因子、內部 witness 不進一般 tooltip 或匯出。可行路線的最好值、分布預估與實際結果須分開標示。

## 待決與准入條件

本功能未新增數值決策。仍須核真 consumer 的量尺、事件順序、TP 交易協作與季度提交位置，不宣稱歷史 trial 表等於現行產品。跨季跳時只在本操作實際依賴跳時時要求 DEC-R5-S04，不把它擴大成既有單回合的全面阻擋。所有文件完成後，仍須正式准入及實跑產品、存讀、UI 測試。

## 重入優先序與數值型別補充

所有會變更狀態的入口，先查同idempotencyKey＋payload及canonical businessEvent是否已有提交結果；已提交同內容必回原receipt，即使請求的expectedRevision已舊也不能先拒。相同key異payload必衝突；不同key同業務事件不得多領。只有尚未提交的新命令才驗目前expectedRevision；pending先查marker再續原交易，不重抽結果。這項順序優先於上文新操作驗證步驟，不能先套active／alive／未selected等前置條件把成功重送當非法新行動。

儲存型別BodyTicks為整數；Talent與能力點可有精確小數，不要求顯示點一律integer。一能力點＝10000ticks，跨單位先明確換算；中間Fraction不得從畫面ppm或浮點近似回灌。
